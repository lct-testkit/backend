Ниже подробная спецификация бэкенда, основанная строго на new_spec.md, dop.md и исходном кейсе ИТ Школы Ростелекома. Она заменяет укрупнённые спринты и описывает, какие модели данных, схемы запросов и ответов, эндпоинты и поведения должны быть реализованы. Фронтенд, вёрстка и дизайн в этот объём не входят, но бэкенд обязан предоставить полный OpenAPI-контракт для SvelteKit BFF, публичных страниц подписания и проверки подписи.

Источником истины являются new_spec.md и dop.md, поэтому все сущности, роли, воронки, механизмы аудита, ПЭП, ЕГРЮЛ, 152-ФЗ и инфраструктурные ограничения берутся из них. Если исходный кейс использует термины «вуз», «ИТ-программа», «ИТ-продукт», «вендор», «номер договора», «срок лицензии» и «статус по передаче», они не превращаются в отдельные противоречащие сущности, а отображаются на модель из new_spec: вуз является organization с org_type university, ИТ-направление является direction, образовательная программа и продукт описываются products и при необходимости типизируются через custom_field_defs, договорные и лицензионные атрибуты хранятся в custom_fields сделок, продуктов или организаций, а подписанные документы прикрепляются через attachments с категориями contract, act, license, presentation, other. Такой подход сохраняет соответствие новой архитектуре и закрывает поля импорта и отчётов из кейса.

Стек фиксируется как Python 3.12, FastAPI, Uvicorn, PostgreSQL 16, Redis 7, SeaweedFS как S3-совместимое хранилище, Keycloak 25, arq для фоновых задач и планировщика, Caddy как TLS-терминация и единая точка входа. Использование MinIO вместо SeaweedFS не допускается, потому что в new_spec выбран именно SeaweedFS из-за лицензии и эффективности на мелких файлах. Приложение является модульным монолитом с пакетами identity, crm, workflow, catalog, reporting, integration, notification, audit, signing, admin. Кросс-модульные вызовы идут только через сервисные интерфейсы, прямой импорт чужих репозиториев запрещён. Все даты хранятся как timestamptz, первичные ключи являются UUIDv7, денежные суммы хранятся как numeric(14,2) с валютой, soft delete реализуется через deleted_at и частичные индексы, все внешние ключи по умолчанию используют ON DELETE RESTRICT, если явно не описано иное.

Все ошибки отдаются в формате RFC 7807 Problem Details. В теле обязательно присутствуют type, title, status, detail, instance, request_id и внутренний код вида CRM-XXYY. Стектрейсы наружу не отдаются. Для валидации используется общий код, например CRM-1001, для конфликта версии используется CRM-1002, для ошибок авторизации и прав используются CRM-1101 и CRM-1102, для ошибок переходов используются CRM-1201, CRM-1202, CRM-1203, для файлов используются CRM-1401 и CRM-1402, для интеграций и дублей используются отдельные коды. Каждый мутирующий эндпоинт принимает заголовок Idempotency-Key, если он создаёт ресурс или запускает необратимую операцию. Обновление объектов использует If-Match и поле version. Списки используют курсорную пагинацию через limit и cursor, а не OFFSET. Каждая выборка ограничивается скоупом пользователя на уровне SQL-запроса. Аудит пишется в той же транзакции, что и бизнес-изменение. Асинхронная запись аудита допускается только как гарантированный транзакционный outbox, но по умолчанию аудит создаётся непосредственно в транзакции изменения данных.

Аутентификация строится по BFF-паттерну из new_spec. Браузер не получает доступные токены в JavaScript-контексте. Сессия хранится в Redis, а в браузер отдаётся только httpOnly, Secure, SameSite=Lax cookie с идентификатором сессии. FastAPI валидирует JWT локально по кэшированному JWKS и не обращается в Keycloak на каждый запрос. При первом входе выполняется just-in-time provisioning локальной записи пользователя. Роли из Keycloak используются для первичной проверки, но окончательное решение принимает API с учётом владельца сделки, команды, региона, участия и объекта. Используются роли KAM, HEAD, ADMIN, AUDITOR, INTEGRATION. Роль KAM соответствует пользователю из кейса, HEAD соответствует руководителю, ADMIN соответствует администратору платформы. AUDITOR является отдельной ролью только для чтения аудита, а INTEGRATION является сервисной ролью для входящих и исходящих интеграций.

Эндпоинт POST /api/auth/callback обрабатывается BFF-слоем и завершает OIDC-поток. Он принимает авторизационный код и состояние, сверяет state, обменивает код на токены в Keycloak с использованием конфиденциального клиента и PKCE, валидирует id_token по подписи, iss, aud, nonce и exp, создаёт серверную сессию в Redis и устанавливает сессионную cookie. Если пользователь впервые появляется в системе, создаётся запись users со статусом invited или active в зависимости от данных приглашения. Если пользователь обязан принять политику обработки ПДн и ещё не принял её, ответ содержит признак consent_required, и фронтенд обязан показать модальное окно согласия до продолжения работы.

Эндпоинт POST /api/auth/logout завершает текущую сессию, удаляет запись сессии из Redis, очищает cookie и вызывает logout в Keycloak для завершения всех сессий пользователя в realm. Если запрошен выход только из текущего приложения, параметр может указывать локальный выход, но по умолчанию используется single logout. Эндпоинт POST /api/auth/backchannel-logout принимает Logout Token от Keycloak, проверяет его подпись и назначение, находит связанные серверные сессии и удаляет их. Этот эндпоинт обязателен, чтобы блокировка или выход пользователя на стороне Keycloak немедленно завершали сессии в CRM.

Эндпоинт GET /api/me возвращает профиль текущего пользователя, включая id, full_name, display_name, email, role, team_id, manager_id, status, locale, timezone, consent_version, признак необходимости принять новую политику, набор скоупов и список активных команд. Ответ строится из локальной таблицы users и данных токена. Если пароль пользователя истёк или есть невыполненное required action в Keycloak, API отвечает ограниченным профилем и признаком, что требуется смена пароля, а бизнес-запросы с неполным доступом отклоняются. Эндпоинт GET /api/me/recent возвращает последние открытые пользователем сделки, организации, контакты и отчёты из Redis-структуры recent:{user_id}. Этот эндпоинт реализует требование кейса о кэше действий пользователя и быстрой загрузке ранее открытых карточек.

Эндпоинт GET /api/me/sessions возвращает список активных серверных сессий пользователя из Redis и связанных данных: идентификатор сессии, устройство, IP, User-Agent, время создания и последнюю активность. Эндпоинт DELETE /api/me/sessions/{sid} завершает конкретную сессию, удаляет её из Redis и при необходимости инициирует соответствующее событие безопасности. Пользователь может завершить только свои сессии, администратор может завершить сессии другого пользователя через отдельный административный механизм.

Эндпоинт POST /api/me/password предназначен для добровольной смены пароля. Он принимает текущий пароль, новый пароль и повтор нового пароля. Пароли не логируются, не кэшируются и не попадают в аудит. BFF или API проверяет текущий пароль через Keycloak и устанавливает новый пароль через Keycloak. После успешной смены завершаются все сессии пользователя, кроме текущей, текущая сессия переиздаётся с новым sid, очищается кэш прав, создаются события безопасности PASSWORD_CHANGED и запись аудита, пользователю отправляется уведомление о смене пароля. Если у пользователя были незавершённые запросы на подпись, они аннулируются со статусом void и причиной credentials_changed, что обязательно реализуется в соответствии с dop.md.

Эндпоинт POST /api/me/consent принимает версию политики и хэш текста политики. Он создаёт запись в consents с subject_type user, policy_version, policy_text_hash, accepted_at, ip и user_agent. Если политика отклоняется, пользователь не получает доступ к данным, а сессия завершается или помечается как требующая согласия. При публикации новой версии политики у пользователей с более старой версией поднимается признак необходимости согласия, и GET /api/me снова возвращает consent_required.

Эндпоинт GET /api/admin/users доступен администратору и возвращает список пользователей с фильтрами по роли, команде, статусу, региону, руководителю и тексту запроса. Ответ содержит локальную проекцию пользователя и признаки из Keycloak, например enabled и required actions, если они доступны через Admin API. Эндпоинт POST /api/admin/users создаёт пользователя. Тело запроса содержит full_name, email, role, team_id, manager_id и признак необходимости TOTP. API сначала создаёт пользователя в Keycloak с enabled=true, emailVerified=false и requiredActions UPDATE_PASSWORD и VERIFY_EMAIL, затем создаёт локальную запись users со статусом invited и генерирует одноразовое приглашение. Если создаётся пользователь с ролью ADMIN, операция требует подтверждения вторым администратором по принципу four-eyes. Если Keycloak недоступен, операция откатывается целиком и локальная запись-сирота не создаётся.

Эндпоинт PATCH /api/admin/users/{id} изменяет роль, команду, руководителя, статус, причину статуса и локальные настройки. При смене роли обновляются role mappings в Keycloak и локальное поле role, немедленно удаляется кэш прав и увеличивается users.perm_epoch. Если токен содержит старый набор прав и эпоха прав изменилась, последующие запросы отклоняются с ошибкой token_stale, после чего BFF должен обновить токен и повторить запрос. Если пользователь является последним администратором, понижение роли, блокировка или удаление запрещаются с ошибкой last_admin. Любая смена роли пишется в аудит с старым и новым значением.

Эндпоинт POST /api/admin/users/{id}/block блокирует пользователя. Тело обязательно содержит причину и опционально дату автоматической разблокировки. В Keycloak пользователь отключается, локальный статус становится blocked, все активные сессии завершаются, кэш прав очищается. Сделки пользователя не переназначаются автоматически, но помечаются признаком владельца, требующего внимания. Уведомления, адресованные заблокированному пользователю, эскалируются руководителю. Эндпоинт POST /api/admin/users/{id}/unblock восстанавливает пользователя, снимает признак недоступности владельца и пишет аудит, но не восстанавливает старые сессии автоматически.

Эндпоинт POST /api/admin/users/{id}/reset-password инициирует принудительный сброс пароля. Для пользователя создаётся одноразовая ссылка или письмо восстановления в Keycloak, ответ всегда одинаковый и не раскрывает существование пользователя. После сброса пароля все сессии завершаются без исключений, создаётся событие PASSWORD_RESET, незавершённые запросы подписи аннулируются, а подписи, поставленные за последние 24 часа до сброса при подозрении на компрометацию, могут быть помечены как disputed через отдельный административный процесс.

Эндпоинт POST /api/admin/users/{id}/offboard реализует мастер передачи дел. Он поддерживает режим preview и режим confirm. В режиме preview возвращаются списки сделок, задач, подписок, активных импортов, отчётов и незавершённых запросов подписи, которые держит пользователь, а также предлагаемые критичные объекты. В режиме confirm тело содержит преемника или правила передачи по сделкам. В одной транзакции меняются владельцы сделок, создаются события OWNER_CHANGED, системные комментарии и аудит, незавершённые запросы подписи переназначаются согласно правилам из dop, пользователь получает статус terminated, его учётка отключается в Keycloak, все сессии завершаются. Комментарии, файлы и история сохраняют авторство и не удаляются.

Эндпоинт POST /api/admin/users/{id}/erasure-request создаёт запрос на удаление или обезличивание данных пользователя. Тело содержит режим, правовое основание, причину и комментарий. Система создаёт запись data_erasure_requests и немедленно возвращает отчёт о блокерах: активные сделки, незакрытые задачи, роль последнего администратора, подписи, файлы с персональными данными, договорные обязательства. Если активные сделки существуют, удаление невозможно до завершения передачи дел. Запрос проходит стадии pending, blocked, approved, rejected, completed. Обезличивание выполняется фоновой задачей с чекпоинтами. После выполнения создаётся акт об уничтожении ПДн в PDF, который подписывается ПЭП ответственного и сохраняется бессрочно. Аудит не удаляется никогда.

Модель пользователей и команд включает таблицы users, teams, user_delegations, consents, security_events и data_erasure_requests. Таблица users хранит keycloak_id, email, full_name, display_name, phone, position, role, team_id, manager_id, status, status_reason, avatar_file_id, locale, timezone, perm_epoch, password_changed_at, last_login_at, consent_version, invited_at, activated_at, blocked_at, anonymized_at, created_at, updated_at, deleted_at. Поля keycloak_id и email уникальны для активных записей. Таблица teams хранит name, parent_id, head_id, region_id и поддерживает рекурсивную иерархию. Таблица user_delegations хранит замещение на время отпуска с scope, starts_at и ends_at. Таблица consents хранит согласия пользователей и контактов на обработку ПДн, версию политики, хэш текста, ip и user_agent. Таблица security_events хранит события безопасности, включая неудачные входы, брутфорс, смену пароля, сброс пароля, отказ в доступе, малварь, массовый экспорт и компрометацию ключа подписи. Таблица data_erasure_requests хранит субъекта, причину, правовое основание, дедлайн, статус, блокеры, исполнителя, результат и ссылку на акт.

Эндпоинт GET /api/organizations возвращает список организаций с фильтрами по названию, ИНН, ОГРН, типу, региону, ответственному владельцу, статусу реестра, аккредитации, источнику создания и тексту поиска. Список ограничивается скоупом пользователя. Ответ содержит базовые поля организации и признак активных сделок, если это разрешено скоупом. Эндпоинт POST /api/organizations создаёт организацию. Тело может содержать либо ИНН, либо название и базовые реквизиты. Если передан ИНН, API сначала валидирует контрольную сумму и выполняет поиск через локальный реестр ЕГРЮЛ. Если организация найдена, создаётся организация с полями из реестра, снапшотом реестра, verified_source, verified_at и registry_version. Поля, изменённые пользователем вручную, сохраняются в manual_overrides. Если найден дубль по ИНН, возвращается ошибка с идентификатором существующей организации и предложением открыть её или запросить доступ. Создание организации пишется в аудит.

Эндпоинт GET /api/organizations/{id} возвращает карточку организации, включая реквизиты, регион, ответственного, филиалы, контакты, сделки, реестровый снапшот, статус, дрейф реквизитов и признаки аккредитации. Эндпоинт PATCH /api/organizations/{id} обновляет организацию с If-Match. Если изменяются реестровые поля, изменения могут быть помечены как ручная правка. Если организация имеет активные сделки и удаляется, выполняется только soft delete или архивирование, физическое удаление запрещено. Эндпоинт POST /api/organizations/{id}/apply-drift принимает изменения реквизитов, найденные при сверке с ЕГРЮЛ, обновляет организацию, очищает или уменьшает requisites_drift, пишет уведомление ответственному и создаёт аудит.

Эндпоинт GET /api/organizations/check-duplicate принимает ИНН или ОГРН и возвращает существующую активную, удалённую или похожую организацию. Если найдена организация, доступ к которой запрещён скоупом, ответ не раскрывает чувствительные поля, но возвращает признак существования и предлагает запросить доступ. Если найдены похожие названия с разными ИНН, возвращаются кандидаты с признаком возможного филиала. Этот эндпоинт обязателен для дедупликации по ИНН и реализуется вместе с уникальным индексом по ИНН для активных организаций.

Модель организаций и контактов включает tables organizations, organization_branches, contacts, contact_channels и regions. Organizations хранят name, short_name, org_type, inn, kpp, ogrn, legal_address, actual_address, region_id, website, main_phone, main_email, students_count, external_ids, owner_id, source, import_job_id, search_vector, а также поля из dop: verified_source, verified_at, registry_version_id, registry_snapshot, registry_status, registry_checked_at, requisites_drift, manual_overrides, is_accredited, accreditation_until. Organization_branches хранят филиалы и институты внутри вуза. Contacts хранят first_name, last_name, middle_name, position, email, phone, organization_id, is_decision_maker, is_anonymized, consent_id, source, external_ids. Чувствительные поля контактов шифруются и маскируются в списках. Contact_channels хранят дополнительные каналы связи, включая telegram, whatsapp и дополнительные телефоны. Regions хранят справочник субъектов РФ, федеральный округ и часовой пояс.

Эндпоинт GET /api/contacts возвращает список контактов с фильтрами по организации, должности, признаку лица, принимающего решения, источнику, тексту поиска и статусу anonymized. Телефон и email в списке маскируются. Эндпоинт POST /api/contacts создаёт контакт. Для B2C-контакта организация может быть пустой, но требуется правовое основание обработки и согласие. Для контакта представителя вуза указывается organization_id. При создании контакта с телефоном или email выполняется нормализация телефона к E.164 и валидация email. Эндпоинт PATCH /api/contacts/{id} обновляет контакт с If-Match и пишет аудит. Эндпоинт POST /api/contacts/{id}/reveal возвращает полные контактные данные и доступен только пользователям с правом доступа к контакту. Каждое раскрытие пишется в аудит как отдельное событие доступа к ПДн.

Эндпоинт GET /api/products возвращает справочник продуктов с фильтрами по направлению, коду, названию, формату, активности, срокам действия и тексту поиска. Продукт в терминах кейса может означать образовательную программу, курс, трек или программный продукт, если это зафиксировано в полях и отчётах. Эндпоинт POST /api/products доступен администратору и создаёт продукт с кодом, названием, описанием, direction_id, длительностью, форматом, базовой ценой, сроком действия и признаком активности. Если кейс требует указать вендор или программное обеспечение, эти данные хранятся через custom_field_defs и custom_fields продукта, не создавая отдельную сущность vendor, чтобы не нарушать модель new_spec. Эндпоинт PATCH /api/products/{id} обновляет продукт и пишет аудит. Архивирование продукта выполняется через is_active=false, физическое удаление не используется, если на продукт есть ссылки в сделках или отчётах.

Эндпоинт GET /api/directions возвращает иерархию ИТ-направлений. Эндпоинт POST /api/directions создаёт направление с кодом, названием и родительским направлением. Эндпоинт PATCH /api/directions/{id} обновляет направление. Удаление направления с привязанными продуктами или сделками запрещено, вместо этого выполняется архивирование или перепривязка. Справочник направлений используется в фильтрах сделок, отчётов и дашбордов.

Эндпоинт GET /api/loss-reasons возвращает справочник причин отказа. Эндпоинт POST /api/loss-reasons создаёт причину с кодом, названием, категорией, активностью и порядком сортировки. Причины отказа обязательны для закрытия сделки в статусе lost и используются в аналитике отказов. Эндпоинт PATCH /api/loss-reasons/{id} обновляет причину. Если причина используется в истории, она не удаляется физически, а деактивируется.

Эндпоинт GET /api/holidays возвращает производственный календарь. Эндпоинт POST /api/holidays добавляет дату, название и признак рабочего дня. Этот справочник обязателен для расчёта SLA в рабочих днях. Эндпоинт PATCH /api/holidays/{id} изменяет дату. Изменение производственного календаря влияет на будущие расчёты и требует аудита.

Эндпоинт GET /api/custom-field-defs возвращает определения пользовательских полей для сделок, организаций и контактов. Эндпоинт POST /api/custom-field-defs создаёт поле с кодом, меткой, типом, опциями, обязательностью, валидацией, привязкой к workflow и порядком. Значения хранятся в JSONB-полях deals.custom_fields или аналогичных полях, если это допускается моделью. Перед публикацией поля проверяется уникальность кода в рамках типа сущности. Эндпоинт PATCH /api/custom-field-defs/{id} обновляет поле, а деактивация поля не удаляет уже накопленные значения, но скрывает поле из новых форм. Пользовательские поля используются для атрибутов кейса, таких как номер договора, срок лицензии, подписание лицензии, вендор и ПО, если они не покрываются базовыми таблицами.

Модель каталога включает products, directions, loss_reasons, holidays и custom_field_defs. Products хранят code, name, description, direction_id, duration_hours, format, base_price, is_active, valid_from, valid_to и import_job_id. Directions хранят code, name, parent_id. Loss_reasons хранят code, name, category, is_active, sort_order. Holidays хранят date, name, is_working_day. Custom_field_defs хранят entity_type, code, label, field_type, options, is_required, validation, workflow_id, sort_order, is_active. Все справочники должны поддерживать поиск, пагинацию и аудит изменений.

Эндпоинт GET /api/workflows возвращает список workflow с фильтрами по типу сделки, состоянию, коду и названию. Эндпоинт POST /api/workflows создаёт workflow с code, name, deal_type и состоянием draft. Эндпоинт GET /api/workflows/{id} возвращает граф статусов и переходов, включая узлы, рёбра, SLA-правила, действия, условия и признаки архивированных статусов. Эндпоинт PUT /api/workflows/{id}/graph сохраняет черновик графа. Тело содержит массив статусов и массив переходов. Каждый статус имеет id, code, name, type, color, sort_order, required_fields и is_archived. Каждый переход имеет id, from_status_id, to_status_id, name, allowed_roles, conditions, actions, requires_comment и sort_order. Сохранение черновика не влияет на живые сделки до публикации.

Эндпоинт POST /api/workflows/{id}/validate проверяет граф без публикации. Проверяются ровно один начальный статус, минимум один терминальный статус, достижимость всех статусов из начального, отсутствие ловушек, корректность условий, существование полей в условиях, корректность действий и наличие пути для отклонения подписи, если переход использует действие request_signature. Ответ содержит список ошибок и предупреждений. Эндпоинт POST /api/workflows/{id}/publish публикует граф только при успешной валидации. Публикация атомарна, обновляет published_at, published_by и graph_hash, инвалидирует кэш графа. Если публикация происходит при активном редактировании другим пользователем, используется проверка версии графа или If-Match.

Эндпоинт GET /api/workflows/{id}/statuses/{sid}/impact возвращает предпросмотр сопоставления статуса. Ответ содержит количество активных сделок в статусе, список сделок или их идентификаторы, проблемы с обязательными полями целевого статуса, влияние на SLA и предложение целевого статуса. Эндпоинт POST /api/workflows/{id}/statuses/{sid}/archive принимает mapping_rules, включая target_status_id, правила распределения по типу сделки или сумме, sla_mode и fallback_status_id. Если есть активные сделки, создаётся статус-маппинг задача, которая батчами переводит сделки, пишет историю со причиной workflow_migration, системные комментарии и аудит. Статус после успешной миграции помечается archived, физическое удаление статуса запрещено. Если активных сделок нет, статус архивируется немедленно.

Модель workflow включает workflows, workflow_statuses, workflow_transitions, sla_rules и status_mapping_jobs. Workflows хранят code, name, deal_type, state draft/published/archived, is_default, published_at, published_by и graph_hash. Workflow_statuses хранят workflow_id, code, name, type initial/intermediate/won/lost/parked, color, sort_order, required_fields, is_archived, archived_at и replaced_by_status_id. Workflow_transitions хранят workflow_id, from_status_id, to_status_id, name, allowed_roles, conditions, actions, requires_comment, sort_order. Conditions являются декларативным JSON DSL с операторами all, any, field, op, value. Actions являются массивом действий, поддерживающих create_task, notify, request_signature, set_owner, set_field и другие зарегистрированные типы. Sla_rules хранят workflow_id, status_id, max_duration, warn_threshold_pct, escalate_to_role, escalate_to_user_id, channels, count_business_days и is_active. Status_mapping_jobs хранят from_status_id, mapping_rules, affected_count, processed_count, failed_count, status, initiated_by, started_at, finished_at и report.

Эндпоинт GET /api/deals возвращает список сделок с фильтрами по статусу, воронке, типу сделки, организации, контакту, владельцу, продукту, направлению, региону, приоритету, SLA-состоянию, периоду создания, периоду закрытия и тексту поиска. Ответ содержит items и next_cursor. Каждый элемент включает id, number, title, deal_type, workflow_id, status_id, organization_id, contact_id, owner_id, amount, currency, priority, sla_due_at, sla_state, version, created_at и краткие связанные названия. Скоуп применяется на уровне SQL. KAM видит сделки, где он owner или участник. HEAD видит сделки своей команды рекурсивно. ADMIN видит все сделки. AUDITOR не имеет доступа к списку сделок. INTEGRATION имеет доступ только к разрешённым интеграционным операциям.

Эндпоинт POST /api/deals создаёт сделку. Тело содержит title, deal_type, workflow_id или признак использования дефолтного опубликованного workflow для типа сделки, organization_id, contact_id, owner_id, amount, currency, students_planned, expected_close_date, priority, products, custom_fields, source и external_ids. Если сделка создаётся интеграцией, источник и внешние идентификаторы обязательны. Если передан Idempotency-Key, повторный запрос с тем же телом возвращает ранее созданную сделку. При создании сделка получает начальный статус опубликованного workflow, номер человека-читаемого вида, версию 1, событие CREATED и запись аудита. Если для сделки указаны продукты, создаются записи deal_products. Если правила назначения ответственности требуют округления или региона, они применяются до создания.

Эндпоинт GET /api/deals/{id} возвращает карточку сделки. Ответ содержит сделку, статус, доступные действия, владельца, организацию, контакт, продукты, участников, SLA-поля, пользовательские поля, количество комментариев, файлов, задач и подпись статуса, если подпись активна. Чувствительные данные контактов маскируются до вызова reveal. Карточка кэшируется версионным ключом, и при обновлении сделки версия увеличивается, что инвалидирует кэш.

Эндпоинт PATCH /api/deals/{id} обновляет поля сделки и принимает If-Match. Тело может содержать частичный набор полей. Каждое поле проверяется по правам и правилам схемы. Пользовательские поля валидируются по определениям. Если меняется владелец, создаются события и уведомления. Если изменяются поля, влияющие на SLA или подписи, вызываются соответствующие побочные задачи. После успешного обновления увеличивается version, пишется аудит с изменениями и публикуется outbox-событие. При несовпадении версии возвращается ошибка конфликта с актуальными значениями конфликтующих полей.

Эндпоинт GET /api/deals/{id}/available-transitions возвращает переходы, доступные текущему пользователю из текущего статуса. Для каждого перехода возвращаются id, название кнопки, целевой статус, requires_comment, список условий с флагом выполнения и человекочитаемой причиной, а также действия, которые будут выполнены. Фронтенд не принимает решений сам и рисует чек-лист по этому ответу. Эндпоинт использует кэш опубликованного графа и скоуп пользователя.

Эндпоинт POST /api/deals/{id}/transition выполняет переход. Тело содержит to_status_id, обязательный или опциональный комментарий, дополнительные поля для заполнения обязательных полей и файлы, если они нужны. Заголовок If-Match обязателен. Последовательность работы фиксирована: загрузка сделки и версии, проверка версии, проверка существования перехода в опубликованном графике, проверка разрешённых ролей, проверка guard-условий, транзакция с обновлением сделки, записью истории, аудитом, outbox-событием и пересчётом SLA. После коммита асинхронно создаются задачи, уведомления, события интеграций и запросы подписи, если это задано действиями перехода. Целевой бюджет p95 для этого эндпоинта не должен превышать 300 мс при 50 RPS. Ошибки: версия не совпала возвращает конфликт, переход запрещён ролями возвращает ошибку прав, недостижимые условия возвращают валидационную ошибку с перечнем причин, сделка удалена или архивирована возвращает ошибку состояния.

Эндпоинт GET /api/deals/{id}/history возвращает историю статусов и событий. История статусов включает from_status_id, to_status_id, changed_by, reason, comment, duration_in_prev, sla_state_at_change и changed_at. История событий включает смену владельца, добавление файлов, импорт, интеграционные изменения, миграции воронки и действия подписи. История доступна только в рамках скоупа и не изменяется задним числом.

Эндпоинт POST /api/deals/{id}/reassign меняет ответственного сделки. Тело содержит нового владельца и причину. Операция доступна руководителю или администратору, если сделка в их скоупе. Создаются системный комментарий, событие OWNER_CHANGED, уведомление новому владельцу и аудит. Эндпоинт POST /api/deals/bulk/reassign выполняет массовую передачу сделок при увольнении или перераспределении нагрузки. Тело содержит список сделок или фильтр и преемника. Операция выполняется транзакционно или батчами с чекпоинтами, пишет аудит с перечнем идентификаторов и уведомляет участников.

Эндпоинты комментариев включают GET /api/deals/{id}/comments и POST /api/deals/{id}/comments. Список поддерживает треды, пагинацию и фильтрацию по автору, системности и внутреннему признаку. Создание комментария принимает body, parent_id, mentions и is_internal. Упоминания пользователей создают уведомления. Эндпоинт PATCH /api/comments/{id} редактирует комментарий автором и сохраняет ревизию в deal_comment_revisions. Системные комментарии редактировать нельзя. Эндпоинт DELETE /api/comments/{id} выполняет мягкое удаление с причиной для администратора или автора, если это разрешено политикой. Все действия пишутся в аудит. Комментарии являются частью истории согласований, поэтому бесследное изменение текста запрещено.

Модель сделок включает deals, deal_participants, deal_status_history, deal_events, deal_products, deal_comments, deal_comment_revisions и tasks. Deals хранят number, title, deal_type, workflow_id, status_id, organization_id, contact_id, owner_id, created_by, amount, currency, students_planned, expected_close_date, status_changed_at, sla_due_at, sla_state, sla_paused_total, priority, loss_reason_id, closed_at, custom_fields, source, external_ids, version, owner_unavailable, search_vector, а также поля из dop: signature_status и active_signature_document_id. Deal_participants хранят участников с ролью в сделке. Deal_status_history является append-only и хранит переходы, причину, комментарий, время в предыдущем статусе и состояние SLA. Deal_events хранит события ленты активности. Deal_products хранят продукты сделки с количеством, ценой, скидкой и суммой. Deal_comments и revisions хранят текст, автора, треды, упоминания, системность, внутренность и историю правок. Tasks хранят задачи, связанные со сделками, с назначением, сроком, приоритетом, статусом и признаком автоматического создания переходом.

Эндпоинт GET /api/tasks возвращает задачи текущего пользователя или команды в зависимости от скоупа. Фильтры включают статус, просроченность, срок, сделку, приоритет и источник. Эндпоинт POST /api/tasks создаёт задачу вручную или используется внутренним механизмом действий переходов. Эндпоинт PATCH /api/tasks/{id} обновляет задачу, включая назначение, срок и описание. Эндпоинт POST /api/tasks/{id}/complete завершает задачу и пишет аудит. Автоматически созданные задачи сохраняют ссылку на переход и не могут быть удалены бесследно.

Эндпоинты файлов реализуют загрузку без прогона байтов через API. Эндпоинт POST /api/files/upload-intent принимает filename, size_bytes, mime_type, purpose и опционально категорию вложения. Он проверяет разрешённые форматы из кейса, включая png, jpeg, pdf, zip, gzip, rar, doc, docx, xls, xlsx, запрещает SVG, проверяет лимит размера файла и лимит на сделку, создаёт запись files в статусе pending и возвращает presigned PUT URL к SeaweedFS с TTL. Эндпоинт POST /api/files/{id}/commit проверяет фактическое наличие объекта, размер, контрольную сумму sha256, магические байты и ставит задачу антивирусной проверки. После успешной проверки статус меняется на ready, при обнаружении малвари файл перемещается в карантин, создаётся событие безопасности и возвращается ошибка. Эндпоинт GET /api/files/{id}/download-url проверяет право доступа к родительской сущности, признак содержит ПДн и возвращает короткоживущую presigned GET URL. Получение ссылки и скачивание пишутся в аудит. Эндпоинт DELETE /api/files/{id} выполняет мягкое удаление, уменьшает refcount и физически удаляет объект только при refcount равном нулю и после ретеншен-периода. Файлы, закрывающие обязательные условия пройденного перехода или подписанные документы, не удаляются без административного действия и причины.

Эндпоинты вложений включают GET /api/attachments с фильтром по сущности и категории, POST /api/attachments для привязки файла к сделке, организации, контакту, отчёту или запросу удаления, и DELETE /api/attachments/{id} для отвязки. Категории включают contract, presentation, act, license, report, signature_container, other. Полиморфная связь проверяется сервисным слоем и триггерами целостности. Вложения к статусам реализуются как привязка файла к сделке с указанием текущего статуса или события статуса, потому что файлы должны сохраняться в истории и аудите.

Модель файлов включает files и attachments. Files хранят storage_key, bucket, original_filename, mime_type, size_bytes, sha256, refcount, status, scan_result, scanned_at, contains_pd, uploaded_by, created_at, deleted_at. Attachments хранят file_id, entity_type, entity_id, category, description, uploaded_by, created_at. Для дедупликации используется индекс по sha256. Для антивируса используется ClamAV или совместимый сервис в закрытом контуре.

Эндпоинт GET /api/org-lookup/suggest возвращает предложения организаций по названию или ИНН. Параметры: q и limit. Эндпоинт ограничен по частоте и пишет каждый запрос в org_lookup_log. Внутри вызывается цепочка провайдеров из dop: сначала локальный реестр ЕГРЮЛ, затем внутренние подтверждённые организации, затем опциональные внешние провайдеры только если включён feature flag, и mock для тестов. Ответ содержит список кандидатов с ИНН, названием, регионом, статусом и признаком ликвидации. Ликвидированные организации показываются с предупреждением, потому что это важная информация для менеджера. Эндпоинт GET /api/org-lookup/inn/{inn} сначала проверяет контрольную сумму ИНН и затем возвращает полные детали из локального реестра, включая ОГРН, КПП, название, ОПФ, статус, адрес, ОКВЭД, руководителя и версию реестра. Эндпоинт POST /api/org-lookup/validate принимает ИНН, ОГРН, ОГРНИП или КПП и возвращает результат проверки контрольных сумм и формата. Валидация выполняется и на бэкенде, даже если фронтенд уже проверил поля.

Модель ЕГРЮЛ включает egrul_entries, registry_versions, university_registry и org_lookup_log. Egrul_entries хранят inn как первичный ключ, ogrn, kpp, full_name, short_name, opf_code, opf_name, status, registration_date, termination_date, region_code, legal_address, address_parts, okved_main, okved_extra, director_name, director_position, capital, is_educational, registry_version_id, raw и search_vector. Поле director_name является персональными данными и маскируется в логах и ответах без необходимости. Registry_versions хранят источник выгрузки, файл, дату публикации, дату импорта, количество записей, импортировавшего пользователя и контрольную сумму. University_registry хранит лицензию, аккредитацию, тип учредителя, формы обучения, коды направлений, число студентов, число кампусов и связь с ЕГРЮЛ по ИНН. Org_lookup_log хранит пользователя, маскированный запрос, провайдера, число результатов, найденный ИНН, время ответа и создан. Для поиска используются GIN по полнотекстовому вектору и триграммный индекс по короткому названию.

Эндпоинт POST /api/admin/registry/import загружает новую выгрузку ЕГРЮЛ или реестра Рособрнадзора. Тело содержит file_id и источник. Создаётся запись registry_versions, затем фоновая задача парсит XML потоково, вставляет данные батчами, проверяет контрольные суммы, фильтрует образовательные ОКВЭД для уменьшения объёма и обновляет поисковые векторы. Эндпоинт GET /api/admin/registry/versions возвращает список версий реестра с датами, числом записей и контрольными суммами. После импорта запускается или планируется сверка реквизитов организаций. Если статус организации меняется на ликвидируется или ликвидирована и есть активные сделки, создаётся уведомление высокого приоритета, задача юристу и флаг в карточке организации.

Эндпоинты импорта каталогов реализуют требования кейса и new_spec. Эндпоинт POST /api/imports принимает file_id, entity_type и режим. Entity_type может быть organizations, products, directions, users, deals или другим каталогом, если он описан в системе. Режим может быть insert, upsert или update. Файл должен быть предварительно загружен через upload-intent. Поддерживаются xls и xlsx. Парсер использует openpyxl в read_only для xlsx и xlrd для xls, определяет кодировку для csv и поддерживает CP1251 и UTF-8-BOM. Проверяются магические сигнатуры, лимит размера, лимит строк, защита от zip-bomb и запрет формул. Эндпоинт GET /api/imports/{id} возвращает состояние импорта, число строк, ошибки, предупреждения, успешные строки, ссылки на результат и доступность отката.

Эндпоинт POST /api/imports/{id}/mapping принимает сопоставление колонок файла с полями системы, пресет маппинга и правила преобразования значений. Для кейса обязательно поддерживаются колонки: название ВУЗа, вендор, ПО, номер договора, подписание лицензии, срок действия лицензии, статус по передаче, ФИО менеджера, ответственные от ВУЗа, комментарий. Название ВУЗа маппится в organizations.name или организации по ИНН. ПО и продукт маппятся в products или custom_fields. Вендор сохраняется как организация или пользовательское поле, если отдельная сущность вендора не используется. Номер договора и срок лицензии сохраняются в custom_fields сделки или организации. Статус по передаче маппится на статусы опубликованного workflow через словарь значений. Ответственные от ВУЗа создают или связывают контакты с признаком представителя вуза. ФИО менеджера связывается с users по ФИО и команде. Комментарий создаёт комментарий сделки или организации. Автоподбор маппинга использует нечёткое совпадение имён колонок и словарь синонимов. Маппинг сохраняется в import_presets.

Эндпоинт POST /api/imports/{id}/dry-run выполняет валидацию без записи. Он проверяет типы, обязательность, форматы ИНН, ОГРН, email, телефонов, дат, дубли внутри файла, коллизии с базой и обогащение строк по ИНН из локального ЕГРЮЛ. Ответ содержит количество корректных строк, предупреждений и ошибок, а также ссылку на файл с ошибками, где к исходным строкам добавлена колонка причины. Если в строке найден существующий ИНН, строка помечается как дубль и может быть обработана стратегией upsert или пропущена. Если статус по передаче не найден, строка считается ошибочной или требует ручного сопоставления.

Эндпоинт POST /api/imports/{id}/apply запускает применение импорта. Тело содержит стратегию обработки дублей, подтверждение маппинга и параметры отката. Применение выполняется батчами с чекпоинтами. Ошибочные строки пропускаются и не откатывают весь импорт. Для изменённых записей сохраняется before_snapshot в import_row_results, что делает откат возможным. После завершения создаётся отчёт, статистика и файл с ошибочными строками. Эндпоинт POST /api/imports/{id}/rollback откатывает импорт по import_job_id: созданные записи помечаются или удаляются безопасно, изменённые записи восстанавливаются из before_snapshot, если это не нарушает целостность связей. Откат пишется в аудит и может требовать подтверждения по принципу необратимых операций.

Модель импорта включает import_jobs, import_row_results и import_presets. Import_jobs хранят file_id, entity_type, mode, mapping, status, total_rows, ok_rows, warn_rows, error_rows, result_file_id, initiated_by, started_at, finished_at, rollback_available, rolled_back_at и источник формата. Import_row_results хранят номер строки, статус, entity_id, before_snapshot и ошибки. Import_presets хранят имя, тип сущности, маппинг, автора и дату создания. Импорт каталогов должен выдерживать 5000 строк без падений и корректно работать с битыми файлами и CP1251.

Эндпоинт GET /api/reports возвращает список доступных отчётных шаблонов и ранее созданных отчётов пользователя. Эндпоинт POST /api/reports создаёт задание отчёта. Тело содержит template_code, формат, параметры периода, вузов, направлений, продуктов, программ, ответственных, статусов и регионов. Форматы включают xls, xlsx, pdf, json для табличного результата и png или pdf для графиков. Если отчёт лёгкий и может быть выполнен быстро, он возвращается синхронно. Если отчёт тяжёлый, возвращается статус принятой задачи и идентификатор. Тяжёлые отчёты выполняются в очереди с ограничением не менее 10 параллельных заданий. Если очередь перегружена, новые задания ожидают, а не роняют систему. Каждая генерация отчёта пишется в аудит с параметрами, числом строк и категориями данных. Содержимое отчёта фильтруется скоупом пользователя. Готовый файл хранится в SeaweedFS, а ссылка на него является одноразовой и короткоживущей. Файлы автоудаляются через 7 дней.

Эндпоинт GET /api/reports/{id} возвращает статус задания, прогресс, число строк, формат, ошибку и время истечения ссылки. Эндпоинт GET /api/reports/{id}/download возвращает короткоживущую ссылку на файл или редирект на presigned URL. Перед выдачей проверяется право пользователя на отчёт, срок хранения и статус задания. Скачивание пишется в аудит. Если отчёт содержит ПДн, доступ к нему возможен только при наличии прав, а выгрузка массива ПДн может требовать подтверждения ПЭП согласно контуру внутренних согласований из dop.

Модель отчётности включает report_templates, report_jobs, dashboards и dashboard_widgets. Report_templates хранят code, name, description, query_def, allowed_roles, default_params и output_formats. Report_jobs хранят template_code, params, format, requested_by, status, progress_pct, row_count, file_id, error, expires_at, created_at и finished_at. Dashboards хранят имя, владельца и признак общего доступа. Dashboard_widgets хранят тип, конфигурацию и позицию. Отчёт по кейсу обязательно поддерживает колонки: наименование вуза, ИТ-направление, ИТ-продукт, статус работы с вузом, ответственный. Графики выгружаются серверным matplotlib или аналогом, а не скриншотом браузера. Дашборды используют кэш агрегатов в Redis и материализованные представления с периодическим обновлением.

Эндпоинты интеграций реализуют входящий поток с сайта и LMS. Эндпоинт POST /api/v1/integrations/cms/leads принимает лиды с сайта на Laravel CMS. Он проверяет HMAC-SHA256 подпись, принимает заголовок Idempotency-Key, сохраняет сырое тело в inbound_messages, выполняет дедупликацию по источнику и внешнему идентификатору, затем создаёт контакт и сделку в B2C-workflow или привязывает лид к существующей сущности. Ответ должен быть идемпотентным и не создавать дубли при повторной доставке. Эндпоинт может возвращать принятый статус, если обработка выполняется асинхронно.

Интеграция с LMS реализуется фоновой задачей, которая периодически вызывает внешний контракт с курсором updated_since, сохраняет курсор в sync_cursors и обновляет learning_progress. При переходе сделки в статус запуска обучения система отправляет событие зачисления в LMS через outbox. Если контракт отдаёт ошибку, задача повторяется с экспоненциальной задержкой, а после нескольких неудач событие попадает в dead letter и создаёт алерт. Эндпоинт POST /api/v1/integrations/lms/progress может использоваться мок-сервисом или внутренней эмуляцией для приёма прогресса, если контракт меняется на событийный. Данные прогресса включают контакт, сделку, продукт, внешний курс, процент, оценку, завершение и последнюю активность.

Модель интеграций включает integration_sources, inbound_messages, outbox_events, external_refs, sync_cursors и learning_progress. Integration_sources хранят код источника, имя, базовый URL, тип аутентификации, ссылку на секрет, активность, конфигурацию, время последней синхронизации и последнюю ошибку. Inbound_messages хранят сырой payload, подпись, статус обработки и ошибку. Outbox_events хранят тип агрегата, идентификатор агрегата, тип события, payload, целевую систему, статус, попытки, время следующей повторной доставки и ошибки. External_refs хранят соответствие наших идентификаторов внешним идентификаторам по типу сущности и источнику. Sync_cursors хранят курсоры ресурсов. Learning_progress хранит прогресс обучения из LMS. Ядро не знает напрямую о Bitrix, CMS или LMS; оно работает только с этими абстракциями.

Эндпоинты администрирования интеграций включают GET /api/admin/integrations/sources, POST /api/admin/integrations/sources, PATCH /api/admin/integrations/sources/{id}, POST /api/admin/integrations/sources/{id}/test и POST /api/admin/integrations/sources/{id}/sync-now. Создание источника сохраняет ссылку на секрет, а не сам секрет. Тест проверяет доступность и формат ответа. Принудительная синхронизация запускает задачу с курсором и пишет журнал. Журнал синхронизаций доступен администратору и включает успешные и ошибочные операции.

Эндпоинты уведомлений включают GET /api/notifications, POST /api/notifications/read, GET /api/me/notification-prefs и PUT /api/me/notification-prefs. Список уведомлений фильтруется по прочитанности, приоритету, типу события и сущности. Чтение может быть массовым по идентификаторам или по фильтру. Настройки пользователя определяют каналы и тихие часы для каждого типа события. Шаблоны уведомлений администрируются через отдельный административный контур. Доставка выполняется через очередь и сохраняет попытки в notification_deliveries. Одно событие может доставляться в несколько каналов, и каждый канал имеет собственный статус. Уведомления, связанные с критичными событиями ликвидации организации, нарушения SLA, отказа подписи и компрометации, имеют высокий приоритет.

Модель уведомлений включает notification_templates, notifications, notification_deliveries и user_notification_prefs. Notification_templates хранят код, канал, шаблон темы, шаблон тела, локаль и активность. Notifications хранят получателя, шаблон, сущность, payload, приоритет, прочитанность и время. Notification_deliveries хранят уведомление, канал, маскированный адрес, статус, попытку, ошибку и время отправки. User_notification_prefs хранят пользователя, событие, каналы, активность и тихие часы.

Эндпоинты подписания реализуют ПЭП из dop. Эндпоинт POST /api/signature-documents создаёт документ на подпись. Тело содержит либо шаблон и данные сущности, либо file_id, а также title, entity_type, entity_id, список подписантов, порядок подписания и дедлайн. Если используется шаблон, сервер рендерит HTML через Jinja2 и генерирует PDF, считает sha256 и сохраняет файл в бакет с запретом перезаписи и удаления для сервисной роли. Если используется загруженный файл, он проверяется как PDF и фиксируется по хэшу. Создаётся запись signature_documents в статусе draft. Эндпоинт GET /api/signature-documents/{id} возвращает состояние документа, хэш, список подписантов, дедлайн, причины блокировки и ссылки на протокол, если он уже создан.

Эндпоинт POST /api/signature-documents/{id}/send запускает сбор подписей. Для внутренних подписантов создаются уведомления в интерфейсе и по разрешённым каналам. Для внешних подписантов создаётся одноразовая ссылка, в базе хранится только sha256 токена. Перед отправкой внешнего запроса проверяется наличие действующего edm_agreements для организации или контакта. Если соглашения нет, документ переводится в статус blocked_no_agreement, а инициатор получает инструкцию оформить соглашение. Эндпоинт POST /api/signature-documents/{id}/void аннулирует документ без удаления. Он доступен руководителю или администратору, требует причину и создаёт отрицательную запись по аналогии с бухгалтерским сторно.

Эндпоинт GET /api/me/signature-requests возвращает задачи текущего пользователя на подпись. Эндпоинт POST /api/signature-requests/{id}/view фиксирует факт ознакомления, время, IP и User-Agent. Без фиксации ознакомления подпись не считается доказуемой. Эндпоинт POST /api/signature-requests/{id}/challenge запрашивает одноразовый код. Код генерируется, хранится как bcrypt-хэш с солью, имеет TTL 5 минут, максимум три попытки и ограничения по частоте. Канал доставки берётся из заранее верифицированных контактов и не может быть изменён в момент подписания. Если канал недоступен после разрешённого числа повторов, используется fallback-канал из contact_channels, если это разрешено.

Эндпоинт POST /api/signature-requests/{id}/sign принимает код подтверждения. Он проверяет код, повторно пересчитывает хэш файла и сверяет его с content_hash. Если хэш не совпадает, возвращается конфликт, документ не подписывается и создаётся инцидент безопасности. Если код верен и хэш совпадает, создаётся подпись в таблице signatures с полным evidence: подписант, документ, метод, маскированный канал доставки, время отправки и проверки кода, число попыток, IP, User-Agent, время ознакомления, данные соглашения и источник времени. Подпись содержит HMAC-метку целостности, версию ключа и ссылку на предыдущий хэш в цепочке. После подписания статус запроса обновляется, а если все подписанты завершили процесс, документ становится signed. Асинхронно создаются протокол, штамп на последней странице, JSON-манифест, outbox-событие DOCUMENT_SIGNED, запись аудита и уведомления участникам.

Эндпоинт POST /api/signature-requests/{id}/reject отклоняет подпись с обязательной причиной. Если документ был частью перехода воронки, сделка возвращается на предыдущий статус или на статус, указанный правилом отказа, создаётся системный комментарий с причиной и уведомление инициатору. Эндпоинт GET /api/signature-documents/{id}/protocol возвращает протокол подписания в PDF, если документ подписан или аннулирован. Протокол содержит кто, когда, с какого IP, каким способом, хэш документа и код проверки.

Публичные эндпоинты подписания доступны без авторизации, но защищены отдельным rate-limit. GET /public/sign/{token} отдаёт страницу или данные для страницы подписания: превью документа, реквизиты, список подписантов, текст соглашения о применении ПЭП и кнопки подписать или отклонить. Токен не хранится в открытом виде. Фиксируются просмотр, время, IP и User-Agent. POST /public/sign/{token}/challenge запрашивает код. POST /public/sign/{token}/sign подтверждает подпись кодом. POST /public/sign/{token}/reject отклоняет документ с причиной. Страница подписания должна использовать строгий CSP и локальный рендерер PDF без внешних ресурсов.

Эндпоинты проверки подписи включают GET /public/verify/{signature_id} и POST /api/signatures/verify. Публичная страница проверки раскрывает только факт подписи, ФИО подписанта или снимок подписанта, дату, хэш документа и статус действительна, отозвана или оспорена. Форма проверки позволяет загрузить файл и сверить его хэш с сохранённым. Программная проверка принимает файл и возвращает результат сверки, включая статус подписи и причину недействительности. Эти эндпоинты обязательны для демонстрации юридической проверяемости ПЭП.

Модель ПЭП включает edm_agreements, signature_templates, signature_documents, signature_requests, signature_otp_codes и signatures. Edm_agreements хранят тип стороны, идентификатор стороны, номер соглашения, файл, способ заключения, даты подписания и действия, статус, причину отзыва и автора. Signature_templates хранят код, имя, тип документа, шаблон тела, обязательные роли подписантов, дедлайн, формат и версию. Signature_documents хранят тип, шаблон, название, сущность, исходный файл, content_hash, подписанный файл, протокол, манифест, порядок подписания, статус, дедлайн, автора, причину аннулирования. Signature_requests хранят документ, тип подписанта, пользователя или контакт, роль, снимок имени, маскированный идентификатор, порядок, хэш токена, срок токена, статус, времена отправки, просмотра и решения, причину отказа и соглашение. Signature_otp_codes хранят хэш кода, соль, канал, маскированный адрес, попытки, максимум попыток, срок и потребление. Signatures являются неизменяемыми и хранят запрос, документ, хэш, метод, отображение подписанта, подпись, алгоритм, evidence, время, источник времени, дрейф времени, IP, User-Agent, признак disputed, предыдущий хэш и текущий хэш. Права на уровне БД разрешают только вставку и чтение подписей, кроме отдельной процедуры пометки disputed.

Эндпоинты администрирования соглашений включают GET /api/admin/edm-agreements и POST /api/admin/edm-agreements. Администратор может создать, просмотреть, отозвать или обновить соглашение об ЭДО. Действующее соглашение является блокирующим условием для внешней подписи. Аудиторий может читать соглашения, но не управлять ими. Каждое изменение соглашения пишется в аудит.

Эндпоинты аудита включают GET /api/admin/audit и экспорт аудита. GET принимает фильтры по актору, роли, сущности, идентификатору, действию, периоду, результату и request_id. Доступ имеют ADMIN, AUDITOR и частично HEAD в рамках команды. Экспорт аудита создаёт отдельный отчёт и пишет событие массового экспорта. Аудит нельзя изменить или удалить через API. Каждая запись содержит предыдущий хэш и собственный хэш, что делает вырезание записи обнаружимым. Чувствительные значения маскируются. Отказы в доступе также записываются.

Модель аудита включает audit_log, feature_flags, system_settings и idempotency_keys. Audit_log партиционируется по месяцам и хранит created_at, actor_id, actor_role, impersonated_by, action, entity_type, entity_id, changes, result, ip, user_agent, request_id, prev_hash и hash. Поле actor_id не имеет жёсткой внешней ключевой ссылки, чтобы переживать обезличивание. Роль приложения имеет только INSERT и SELECT на таблицу аудита. Feature_flags хранят код, активность, описание, раскатку и автора изменения. System_settings хранят ключ, JSON-значение, описание, признак секрета и автора изменения. Idempotency_keys хранят ключ, хэш запроса, статус ответа, тело ответа и срок жизни.

Эндпоинты системных настроек и флагов включают GET /api/admin/feature-flags, PATCH /api/admin/feature-flags/{code}, GET /api/admin/system-settings и PUT /api/admin/system-settings/{key}. Изменение настройки или флага доступно администратору и пишется в аудит. Секретные значения не возвращаются в открытом виде. Через системные настройки могут управляться порядок провайдеров автоподстановки, лимиты отчётов, лимиты публичной подписи и параметры SLA.

Эндпоинты задач и дашбордов включают GET /api/dashboards, POST /api/dashboards, GET /api/dashboards/{id}, PUT /api/dashboards/{id}, POST /api/dashboards/{id}/widgets и DELETE /api/dashboards/{id}/widgets/{widgetId}. Дашборд может быть личным или общим. Данные для виджетов возвращаются агрегированными и не содержат лишних ПДн. Для тяжёлых агрегатов используются материализованные представления и кэш. Аналитические эндпоинты могут включать воронку, динамику, рейтинг программ или продуктов, географию, длительности статусов и нагрузку менеджеров, но все они должны соблюдать скоуп пользователя и не раскрывать ФИО без необходимости.

Эндпоинты здоровья и документации включают GET /health/live, GET /health/ready и GET /metrics. Эндпоинт здоровья проверяет соединение с БД, Redis, Keycloak JWKS, SeaweedFS и очередь. Метрики отдаются в формате Prometheus и включают RED-метрики, длину очереди, время импорта, нарушения SLA и hit-rate кэша. OpenAPI публикуется на /api/openapi.json и /api/docs. Каждая ручка имеет схемы запроса и ответа, коды ошибок, требования авторизации и описание идемпотентности. Это выполняет требование кейса о Swagger и перечне использованных методов.

## 1. Что должно быть понятно бекендеру до начала кодинга

Бекенд — это не просто набор CRUD-ручек. Это закрытая корпоративная система, где почти каждое действие должно быть проверяемым: кто сделал, когда сделал, на основании чего, какие данные изменил, какие права имел и не нарушил ли контур 152-ФЗ.

Система должна быть модульным монолитом. Это значит один деплойный артефакт `api`, но внутри строгая структура модулей: `identity`, `crm`, `workflow`, `catalog`, `reporting`, `integration`, `notification`, `audit`, `signing`, `admin`. Каждый модуль имеет свои роутеры, сервисы, репозитории, схемы и тесты. Модуль не должен напрямую импортировать репозитории другого модуля. Общение между модулями идёт через сервисные интерфейсы. Это важно, потому что в будущем любой модуль можно будет вынести отдельно без переписывания.

Все бизнес-изменения должны быть атомарными. Если меняется сделка, статус, владелец, файл, подпись, пользователь или запрос на удаление, то в одной транзакции должны происходить: изменение данных, запись в историю, если она есть, запись в аудит, запись в `outbox_events`, если событие должно уйти наружу. Нельзя сначала изменить сделку, а потом где-то в фоне пытаться записать аудит и надеяться, что очередь не упала.

Все списки должны быть быстрыми. Это значит курсорная пагинация, частичные индексы, отсутствие `OFFSET`, отсутствие `SELECT *`, отсутствие запросов внутри цикла, явная загрузка связей и расчёт вычисляемых полей в SQL, если это возможно.

Все чувствительные данные должны маскироваться в логах, ответах без прав и аудите. Телефоны показываются как `+7 (9**) ***-**-12`, email как `i***@domain.ru`, ФИО при обезличивании заменяется на стабильный псевдоним вида `Пользователь #4821`, а не на безликое `Удалён`.

## 2. Базовые соглашения API

Все ручки живут под префиксом `/api`, кроме публичных страниц подписания и проверки, которые могут быть под `/public`. Ответы отдаются в JSON. Для файлов и выгрузок могут быть редиректы или выдача одноразовых ссылок.

Формат дат и времени — только `ISO 8601` с часовым поясом, в базе всё хранится как `timestamptz`. В JSON даты приходят как строка вида `2026-06-01T12:30:00+03:00` или UTC-формат, но фронтенд должен получать консистентный формат. Внутренне лучше хранить и отдавать UTC.

Деньги в JSON отдаются как строка, например `"150000.00"`, плюс отдельное поле `currency`. Это защищает от проблем с float. В базе тип `numeric(14,2)`.

Идентификаторы — `UUIDv7`. В JSON это строки. Использовать автоинкрементные числа как публичные идентификаторы нельзя. Человекочитаемые номера можно делать только как дополнительные поля, например `number: "D-2026-00431"`.

Все списки используют курсорную пагинацию. Клиент передаёт `limit` и `cursor`. Максимальный `limit` — 100. Ответ списка выглядит как объект с `items` и `next_cursor`. Если дальше элементов нет, `next_cursor` равен `null`. Курсор должен быть непрозрачным для клиента, внутри обычно кодируется пара `created_at` и `id` или `sort_field` и `id`.

Все изменяющие запросы должны поддерживать идемпотентность там, где повтор может создать дубль или запустить необратимое действие. Клиент передаёт заголовок `Idempotency-Key`. Сервер сохраняет ключ, хэш запроса и ответ. Повторный запрос с тем же ключом возвращает сохранённый ответ. В базе для этого есть таблица `idempotency_keys`, а в Redis быстрый кэш.

Все обновления сущностей используют оптимистичную блокировку. Клиент передаёт `If-Match` со значением текущей версии. В ответе сущности всегда есть поле `version`. Если версия не совпала, сервер возвращает `409 Conflict` и в теле показывает актуальные значения конфликтующих полей. Для сделок это особенно важно: два менеджера могут открыть одну карточку.

Все ошибки возвращаются в формате RFC 7807 Problem Details. В теле должны быть поля `type`, `title`, `status`, `detail`, `instance`, `request_id`, `code`, при необходимости массив `errors` с полями и причинами. Внутренний код ошибки имеет формат `CRM-XXYY`. Стектрейсы наружу не отдаются. `request_id` генерируется или прокидывается от Caddy, пишется в логи, аудит и ответ.

## 3. Каталог ошибок

Ниже базовый набор кодов, который нужно завести сразу. Бекендер не должен придумывать коды на лету без этого каталога.

`CRM-1001` — ошибка валидации запроса. Используется, когда тело запроса не прошло схему, поле обязательное, формат неверный, диапазон неверный.

`CRM-1002` — конфликт версии. Используется при несовпадении `If-Match`.

`CRM-1003` — идемпотентный конфликт. Заголовок `Idempotency-Key` уже использовался, но тело запроса отличается.

`CRM-1101` — пользователь не аутентифицирован.

`CRM-1102` — недостаточно прав.

`CRM-1103` — токен устарел из-за смены роли или прав, нужно обновить токен.

`CRM-1104` — пользователь заблокирован или уволен.

`CRM-1105` — требуется согласие на обработку ПДн.

`CRM-1201` — переход по воронке недоступен из-за невыполненных условий.

`CRM-1202` — переход по воронке запрещён ролью или настройками перехода.

`CRM-1203` — сделка не активна, удалена, архивирована или уже закрыта.

`CRM-1204` — требуется комментарий при переходе.

`CRM-1205` — требуются обязательные вложения или поля целевого статуса.

`CRM-1206` — требуется подпись, но подпись отсутствует, отклонена или просрочена.

`CRM-1301` — найден дубликат сущности.

`CRM-1302` — организация уже существует по ИНН.

## 4. Роли, скоупы и права

В системе используются роли `KAM`, `HEAD`, `ADMIN`, `AUDITOR`, `INTEGRATION`. Роль хранится в Keycloak и локально в `users.role` для быстрого фильтра. Источник истины по роли — Keycloak, но финальное решение по доступу всегда принимает наш API.

`KAM` — менеджер по вузам. Видит только те сделки, где он владелец или участник. Видит организации и контакты, связанные с его сделками. Может создавать сделки, переходить по статусам своих сделок, добавлять комментарии, файлы, задачи, смотреть уведомления. Не может управлять пользователями, воронками, справочниками и удалять чужие данные.

`HEAD` — руководитель. Видит все сделки своей команды, включая подчинённые команды рекурсивно. Может менять ответственного по сделкам своей команды, смотреть аудит по своей команде, видеть отчёты по команде, согласовывать критичные действия, если это настроено.

`ADMIN` — администратор платформы. Видит всё, управляет пользователями, ролями, воронками, справочниками, интеграциями, импортами, реестрами, соглашениями ЭДО, флагами, настройками, запросами удаления. Некоторые операции требуют второго администратора, например удаление или обезличивание субъекта.

`AUDITOR` — аудит. Может читать аудит-лог и экспорт аудита. Не должен иметь доступ к сделкам, контактам и ПДн в обычном режиме. Если аудитору нужно смотреть карточки, это отдельная настройка, но по умолчанию аудит — только журнал событий.

`INTEGRATION` — сервисная учётка для интеграций. Может создавать лиды и сделки из входящих потоков, обновлять прогресс обучения, получать события через коннектор. Не имеет пользовательского доступа к интерфейсу.

Проверка прав делается на трёх уровнях. Первый уровень — маршрут и базовое право, например `deal:read` или `workflow:publish`. Второй уровень — объект, например может ли пользователь трогать конкретную сделку. Третий уровень — SQL-фильтр списка, который не даёт вернуть чужие объекты даже если проверка объекта забыта.

Для списков обязательно реализуется функция скоупа. Для `KAM` это `owner_id = current_user.id OR exists participant`. Для `HEAD` это рекурсивный список команд через `WITH RECURSIVE`. Для `ADMIN` без ограничения. Для `INTEGRATION` только сущности, созданные этим источником, либо по явному разрешению. Для `AUDITOR` пустой скоуп по сделкам и контактам.

## 5. Модели данных: что обязательно создать

Ниже описаны таблицы и ключевые поля. Это не полный SQL, но достаточный уровень для генерации миграций. Для каждой таблицы по умолчанию есть `created_at`, `updated_at`, если не указано иное. Для большинства сущностей есть `deleted_at` для soft delete.

### 5.1. Identity

Таблица `users` хранит локальную проекцию пользователя. Поля: `id`, `keycloak_id`, `email`, `full_name`, `display_name`, `phone`, `position`, `role`, `team_id`, `manager_id`, `status`, `status_reason`, `avatar_file_id`, `locale`, `timezone`, `perm_epoch`, `password_changed_at`, `last_login_at`, `consent_version`, `invited_at`, `activated_at`, `blocked_at`, `anonymized_at`, `created_at`, `updated_at`, `deleted_at`.

Поле `role` ограничено значениями `KAM`, `HEAD`, `ADMIN`, `AUDITOR`, `INTEGRATION`. Поле `status` ограничено значениями `invited`, `active`, `blocked`, `terminated`, `anonymized`. `keycloak_id` уникален для активных записей, но может становиться `NULL` после обезличивания. `email` уникален среди активных записей. `perm_epoch` увеличивается при смене роли и используется для мгновенного понижения прав.

Таблица `teams` хранит команды. Поля: `id`, `name`, `parent_id`, `head_id`, `region_id`, `created_at`, `updated_at`, `deleted_at`. Иерархия рекурсивная. `HEAD` видит команды вниз по иерархии.

Таблица `user_delegations` хранит замещения. Поля: `id`, `from_user_id`, `to_user_id`, `scope`, `starts_at`, `ends_at`, `created_by`, `created_at`. Поле `scope` задаёт, что именно делегируется: просмотр, переходы, назначение. Право подписи по умолчанию не делегируется.

Таблица `consents` хранит согласия. Поля: `id`, `subject_type`, `subject_id`, `policy_version`, `policy_text_hash`, `accepted_at`, `revoked_at`, `ip`, `user_agent`, `signature_id`, `created_at`. `subject_type` — `user` или `contact`. Для согласий, подписанных ПЭП, заполняется `signature_id`.

Таблица `security_events` хранит события безопасности. Поля: `id`, `user_id`, `event_type`, `severity`, `ip`, `user_agent`, `details`, `created_at`. Типы: `LOGIN_FAILED`, `BRUTE_FORCE_LOCK`, `PASSWORD_CHANGED`, `PASSWORD_RESET`, `SESSION_HIJACK_SUSPECT`, `PERMISSION_DENIED`, `MALWARE_DETECTED`, `MASS_EXPORT`, `SIGNATURE_OTP_FAILED`, `SIGNATURE_KEY_COMPROMISED`.

Таблица `data_erasure_requests` хранит запросы на удаление или обезличивание. Поля: `id`, `subject_type`, `subject_id`, `reason`, `legal_basis`, `requested_by`, `requested_at`, `deadline_at`, `status`, `rejection_reason`, `blockers`, `executed_at`, `act_file_id`, `act_signature_id`, `created_at`, `updated_at`. Статусы: `pending`, `blocked`, `approved`, `rejected`, `completed`.

### 5.2. Организации и контакты

Таблица `organizations` хранит организации. Поля: `id`, `name`, `short_name`, `org_type`, `inn`, `kpp`, `ogrn`, `legal_address`, `actual_address`, `region_id`, `website`, `main_phone`, `main_email`, `students_count`, `external_ids`, `owner_id`, `source`, `import_job_id`, `search_vector`, `created_by`, `created_at`, `updated_at`, `deleted_at`.

`org_type` может быть `university`, `college`, `company`, `individual_entrepreneur`. Для активных организаций ИНН уникален. Обязательно создать уникальный частичный индекс `UNIQUE(inn) WHERE inn IS NOT NULL AND deleted_at IS NULL`.

Таблица `organization_branches` хранит филиалы. Поля: `id`, `organization_id`, `name`, `address`, `parent_id`, `created_at`, `updated_at`, `deleted_at`.

Таблица `contacts` хранит физлиц. Поля: `id`, `organization_id`, `first_name`, `last_name`, `middle_name`, `position`, `email`, `phone`, `is_decision_maker`, `is_anonymized`, `anonymized_at`, `consent_id`, `source`, `external_ids`, `created_at`, `updated_at`, `deleted_at`. Чувствительные поля шифруются. В списках маскируются. Полные данные выдаются только через `reveal`.

## 6. Эндпоинты: как они должны работать

### 6.1. Профиль и сессии

`GET /api/me` возвращает профиль текущего пользователя. Ответ содержит `id`, `full_name`, `display_name`, `email`, `role`, `team_id`, `manager_id`, `status`, `locale`, `timezone`, `consent_version`, `consent_required`, `scopes`. Если пользователь должен сменить пароль или принять новую политику, это указывается в ответе.

`GET /api/me/recent` возвращает последние открытые сущности пользователя. Ответ содержит список сделок, организаций, контактов и отчётов с типом, идентификатором, названием и временем открытия. Данные берутся из Redis. Это реализует требование кейса про кэш действий пользователя.

`GET /api/me/sessions` возвращает активные сессии пользователя. Каждая сессия содержит идентификатор, устройство, IP, время создания и последнюю активность. `DELETE /api/me/sessions/{sid}` завершает конкретную сессию.

`POST /api/me/password` меняет пароль. Тело: `current_password`, `new_password`, `new_password_repeat`. После успешной смены завершаются все сессии, кроме текущей, текущая сессия переиздаётся, очищается кэш прав, создаются события безопасности и пользовательские уведомления. Незавершённые запросы подписи пользователя аннулируются с причиной `credentials_changed`.

`POST /api/me/consent` принимает согласие на политику. Тело: `policy_version`, `policy_text_hash`. Создаётся запись в `consents`. Если согласие отклонено, пользователь не получает доступ к системе.

### 6.2. Администрирование пользователей

`GET /api/admin/users` возвращает список пользователей. Доступ: `ADMIN`. Фильтры: `role`, `team_id`, `status`, `q`, `manager_id`, `region_id`. Ответ содержит локальные поля и признаки состояния.

`POST /api/admin/users` создаёт пользователя. Тело: `full_name`, `email`, `role`, `team_id`, `manager_id`, `require_totp`. Сначала создаётся пользователь в Keycloak, затем локальная запись. Если создаётся `ADMIN`, требуется подтверждение второго администратора. Если Keycloak недоступен, локальная запись не создаётся.

`PATCH /api/admin/users/{id}` меняет роль, команду, руководителя, статус. При смене роли увеличивается `perm_epoch`, очищается кэш прав. Нельзя понизить или заблокировать последнего администратора.

`POST /api/admin/users/{id}/block` блокирует пользователя. Тело: `reason`, `auto_unblock_at`. Завершаются все сессии, пользователь отключается в Keycloak, сделки помечаются `owner_unavailable`.

`POST /api/admin/users/{id}/unblock` разблокирует пользователя. Старые сессии не восстанавливаются.

`POST /api/admin/users/{id}/reset-password` запускает сброс пароля. Ответ всегда одинаковый, чтобы не раскрывать существование пользователя. После сброса завершаются все сессии, незавершённые подписи аннулируются, создаётся событие безопасности.

`POST /api/admin/users/{id}/offboard` запускает мастер передачи дел. Тело может быть режимом `preview` или `confirm`. В режиме `preview` возвращаются сделки, задачи, активные импорты, отчёты и запросы подписи, которые держит пользователь. В режиме `confirm` указывается преемник или правила передачи. В одной транзакции меняются владельцы сделок, создаются события `OWNER_CHANGED`, системные комментарии, аудит, переназначаются незавершённые подписи, пользователь получает статус `terminated`, его сессии завершаются.

`POST /api/admin/users/{id}/erasure-request` создаёт запрос на удаление или обезличивание. Тело: `mode`, `reason`, `legal_basis`, `comment`. Ответ содержит блокеры. Если есть активные сделки, запрос переводится в `blocked`. Если запрос подтверждён и выполнен, формируется акт уничтожения, который подписывается ПЭП ответственного.

### 6.3. Организации и контакты

`GET /api/organizations` возвращает список организаций. Фильтры: `q`, `inn`, `ogrn`, `org_type`, `region_id`, `owner_id`, `registry_status`, `is_accredited`, `source`, `cursor`, `limit`. Ответ ограничен скоупом.

`POST /api/organizations` создаёт организацию. Тело может содержать `inn` или минимальные реквизиты. Если передан ИНН, сначала проверяется контрольная сумма, затем выполняется поиск в локальном ЕГРЮЛ. Если организация найдена, поля заполняются из реестра, сохраняется `registry_snapshot`, `verified_source`, `verified_at`. Если найден дубль, возвращается `409 CRM-1302` с данными существующей организации.

`GET /api/organizations/{id}` возвращает карточку организации, включая филиалы, контакты, сделки, реестровый статус, дрейф реквизитов и аккредитацию.

`PATCH /api/organizations/{id}` обновляет организацию. Обязателен `If-Match`. Если пользователь вручную меняет реестровые поля, эти поля добавляются в `manual_overrides`.

`POST /api/organizations/{id}/apply-drift` принимает изменения из ЕГРЮЛ. Тело содержит принимаемый диф. После применения обновляются поля, очищается часть `requisites_drift`, создаётся уведомление и аудит.

`GET /api/organizations/check-duplicate` принимает `inn` или `ogrn` и возвращает существующую активную, удалённую или похожую организацию. Если организация недоступна по правам, чувствительные поля не раскрываются, но возвращается признак существования и возможность запросить доступ.

`GET /api/contacts` возвращает контакты с маскированными телефоном и email. Фильтры: `organization_id`, `q`, `is_decision_maker`, `is_anonymized`, `source`.

`POST /api/contacts` создаёт контакт. Для B2C обязательно наличие согласия или правового основания. Для представителя вуза указывается `organization_id`. Телефон нормализуется к E.164, email валидируется.

`PATCH /api/contacts/{id}` обновляет контакт с `If-Match`. Каждое изменение пишется в аудит.

`POST /api/contacts/{id}/reveal` возвращает полные контактные данные. Доступ только если пользователь имеет право видеть контакт. Каждое раскрытие пишется в аудит как `PII_ACCESS`.

### 6.4. Справочники

Для продуктов, направлений, причин отказа, праздников и пользовательских полей делаются стандартные ручки списка, просмотра, создания и обновления. Доступ на чтение — всем аутентифицированным ролям, кроме `INTEGRATION`, если не требуется явно. Доступ на изменение — `ADMIN`.

`GET /api/products` фильтрует продукты по `direction_id`, `q`, `is_active`, `format`, `valid_to`. `POST /api/products` создаёт продукт. `PATCH /api/products/{id}` обновляет. Продукты не удаляются физически, если на них есть ссылки, а деактивируются.

`GET /api/directions` возвращает иерархию. `POST /api/directions` создаёт направление. `PATCH /api/directions/{id}` обновляет. Удаление направления с привязанными продуктами или сделками запрещено.

`GET /api/loss-reasons` возвращает активные причины отказа. `POST /api/loss-reasons` создаёт причину. `PATCH /api/loss-reasons/{id}` обновляет.

`GET /api/holidays` возвращает производственный календарь. `POST /api/holidays` добавляет дату. `PATCH /api/holidays/{id}` изменяет дату. Используется для расчёта SLA в рабочих днях.

`GET /api/custom-field-defs` возвращает определения пользовательских полей. `POST /api/custom-field-defs` создаёт поле. `PATCH /api/custom-field-defs/{id}` обновляет поле. Деактивация не удаляет накопленные значения.

### 6.5. Воронки

`GET /api/workflows` возвращает список воронок. Фильтры: `deal_type`, `state`, `q`.

`POST /api/workflows` создаёт черновик воронки. Тело: `code`, `name`, `deal_type`, `is_default`.

`GET /api/workflows/{id}` возвращает граф: статусы, переходы, SLA-правила, состояние публикации и архивированные статусы.

`PUT /api/workflows/{id}/graph` сохраняет черновик графа. Тело содержит массив `statuses` и массив `transitions`. Каждый статус имеет `id`, `code`, `name`, `type`, `color`, `sort_order`, `required_fields`, `is_archived`. Каждый переход имеет `id`, `from_status_id`, `to_status_id`, `name`, `allowed_roles`, `conditions`, `actions`, `requires_comment`, `sort_order`.

`POST /api/workflows/{id}/validate` проверяет граф. Проверяются один начальный статус, минимум один терминальный статус, достижимость всех статусов, отсутствие ловушек, корректность условий, существование полей в условиях, корректность действий, наличие пути при отклонении подписи, если есть `request_signature`. Ответ содержит `errors` и `warnings`.

`POST /api/workflows/{id}/publish` публикует граф. Публикация возможна только если валидация прошла. Обновляются `published_at`, `published_by`, `graph_hash`, инвалидируется кэш графа.

`GET /api/workflows/{id}/statuses/{sid}/impact` возвращает предпросмотр архивирования статуса. Ответ содержит число активных сделок, список проблемных сделок, недостающие обязательные поля, влияние на SLA и предложения целевых статусов.

`POST /api/workflows/{id}/statuses/{sid}/archive` запускает сопоставление. Тело: `mapping_rules`, `target_status_id`, `fallback_status_id`, `sla_mode`. Если есть активные сделки, создаётся фоновая задача `workflow.status_mapping`. Сделки переводятся батчами, в истории пишется `reason = 'workflow_migration'`, в каждую сделку добавляется системный комментарий. После завершения статус помечается `archived`.

### 6.6. Сделки

`GET /api/deals` возвращает список сделок. Фильтры: `status_id`, `workflow_id`, `deal_type`, `organization_id`, `contact_id`, `owner_id`, `product_id`, `direction_id`, `region_id`, `priority`, `sla_state`, `created_from`, `created_to`, `closed_from`, `closed_to`, `q`, `cursor`, `limit`. Ответ содержит краткие карточки сделок и `next_cursor`.

`POST /api/deals` создаёт сделку. Тело: `title`, `deal_type`, `workflow_id`, `organization_id`, `contact_id`, `owner_id`, `amount`, `currency`, `students_planned`, `expected_close_date`, `priority`, `products`, `custom_fields`, `source`, `external_ids`. Для интеграций обязательны `source` и `external_ids`. Сделка получает начальный статус опубликованной воронки, `version = 1`, событие `CREATED` и аудит.

`GET /api/deals/{id}` возвращает карточку сделки. Ответ содержит сделку, статус, доступные переходы, владельца, организацию, контакт, продукты, участников, пользовательские поля, счётчики комментариев, файлов, задач, состояние подписи и `version`. Чувствительные контакты маскируются.

`PATCH /api/deals/{id}` обновляет сделку. Обязателен `If-Match`. Тело частичное. Каждое поле проверяется по правам и схеме. Если меняется владелец, создаются событие, уведомление и аудит. Если изменяются поля, влияющие на SLA или подпись, запускаются побочные задачи. После успешного обновления увеличивается `version`.

`GET /api/deals/{id}/available-transitions` возвращает доступные переходы. Для каждого перехода возвращаются `id`, `name`, `to_status_id`, `requires_comment`, список условий с флагом `satisfied` и человекочитаемой причиной, а также действия. Фронтенд должен рисовать чек-лист по этому ответу и не принимать решение сам.

`POST /api/deals/{id}/transition` выполняет переход. Заголовки: `If-Match` обязателен, `Idempotency-Key` рекомендуется. Тело: `to_status_id`, `comment`, `fields`, `attachments`. Алгоритм: загрузка сделки, проверка версии, проверка перехода в опубликованном графе, проверка роли, проверка условий, транзакция с обновлением сделки, записью истории, аудита, outbox и пересчётом SLA. После коммита асинхронно создаются задачи, уведомления, события интеграций и запросы подписи, если это задано действиями перехода.

Ошибки перехода: `409 CRM-1002` при конфликте версии, `403 CRM-1102` при запрете ролью, `422 CRM-1201` при невыполненных условиях, `422 CRM-1204` если требуется комментарий, `422 CRM-1205` если требуются поля или файлы, `422 CRM-1206` если требуется подпись.

`GET /api/deals/{id}/history` возвращает историю статусов и событий. История статусов содержит `from_status_id`, `to_status_id`, `changed_by`, `reason`, `comment`, `duration_in_prev`, `sla_state_at_change`, `changed_at`. История событий содержит смену владельца, файлы, подписи, интеграции, импорт и миграции.

`POST /api/deals/{id}/reassign` меняет ответственного. Тело: `owner_id`, `reason`. Доступно `HEAD` или `ADMIN` в рамках скоупа. Создаются системный комментарий, событие `OWNER_CHANGED`, уведомление и аудит.

`POST /api/deals/bulk/reassign` выполняет массовую передачу. Тело: список сделок или фильтр и преемник. Операция выполняется батчами, пишет аудит и уведомления.

`GET /api/deals/{id}/comments` возвращает комментарии. `POST /api/deals/{id}/comments` создаёт комментарий. Тело: `body`, `parent_id`, `mentions`, `is_internal`. `PATCH /api/comments/{id}` редактирует комментарий и сохраняет ревизию. Системные комментарии редактировать нельзя. `DELETE /api/comments/{id}` выполняет мягкое удаление с причиной.

`GET /api/tasks` возвращает задачи. Фильтры: `status`, `deal_id`, `assignee_id`, `due_before`, `overdue`, `priority`. `POST /api/tasks` создаёт задачу. `PATCH /api/tasks/{id}` обновляет. `POST /api/tasks/{id}/complete` завершает.

### 6.7. Файлы и вложения

`POST /api/files/upload-intent` создаёт намерение загрузки. Тело: `filename`, `size_bytes`, `mime_type`, `purpose`, `category`. Проверяются разрешённые форматы, лимит размера и лимит на сделку. Создаётся запись `files` в статусе `pending`. Ответ содержит `file_id` и presigned PUT URL к SeaweedFS с TTL.

Разрешённые форматы файлов по кейсу: `png`, `jpeg`, `pdf`, `zip`, `gzip`, `rar`, `doc`, `docx`, `xls`, `xlsx`. SVG запрещён. Лимит файла — 50 МБ. Лимит на сделку — 500 МБ. Эти значения выносятся в настройки.

`POST /api/files/{id}/commit` завершает загрузку. Эндпоинт проверяет наличие объекта, размер, `sha256`, магические байты, ставит задачу антивирусной проверки. После успешной проверки статус становится `ready`. Если найдена малварь, файл перемещается в карантин, создаётся событие безопасности, возвращается ошибка.

`GET /api/files/{id}/download-url` выдаёт короткоживущую ссылку на скачивание. Перед выдачей проверяется право доступа к родительской сущности. Получение ссылки и скачивание пишутся в аудит.

`DELETE /api/files/{id}` мягко удаляет файл. `refcount` уменьшается. Физическое удаление возможно только когда `refcount = 0` и истёк ретеншен. Файлы, связанные с подписями, пройденными переходами или актами, не удаляются без административного действия.

`GET /api/attachments` возвращает вложения по сущности. `POST /api/attachments` привязывает файл к сделке, организации, контакту, отчёту или запросу удаления. `DELETE /api/attachments/{id}` отвязывает файл.

### 6.8. Импорт

`POST /api/imports` создаёт импорт. Тело: `file_id`, `entity_type`, `mode`. `entity_type` может быть `organizations`, `products`, `directions`, `users`, `deals`. `mode` может быть `insert`, `upsert`, `update`. Файл должен быть загружен через `upload-intent`.

`GET /api/imports/{id}` возвращает состояние импорта: статус, число строк, ошибки, предупреждения, результат, ссылку на файл ошибок и доступность отката.

`POST /api/imports/{id}/mapping` принимает маппинг колонок. Тело содержит массив колонок и правила преобразования значений. Обязательно поддерживаются поля кейса: название ВУЗа, вендор, ПО, номер договора, подписание лицензии, срок действия лицензии, статус по передаче, ФИО менеджера, ответственные от ВУЗа, комментарий.

Маппинг названия ВУЗа идёт в `organizations.name` или поиск организации по ИНН. ПО и продукт маппятся в `products` или `custom_fields`. Вендор сохраняется как пользовательское поле или организация, но не как отдельная базовая сущность. Номер договора и срок лицензии сохраняются в `deals.custom_fields` или `organizations.custom_fields`. Статус по передаче маппится на статусы опубликованной воронки через словарь значений. ФИО менеджера связывается с `users`. Ответственные от ВУЗа создают или связывают контакты. Комментарий создаёт комментарий сделки или организации.

`POST /api/imports/{id}/dry-run` выполняет проверку без записи. Проверяются типы, обязательность, форматы, ИНН, ОГРН, email, телефоны, даты, дубли внутри файла, коллизии с базой, обогащение по ЕГРЮЛ. Ответ содержит число корректных строк, предупреждений и ошибок, а также ссылку на файл ошибок.

`POST /api/imports/{id}/apply` применяет импорт. Применение выполняется батчами. Ошибочные строки пропускаются и не роняют весь импорт. Для изменённых записей сохраняется `before_snapshot`, чтобы был откат.

`POST /api/imports/{id}/rollback` откатывает импорт. Созданные записи помечаются или безопасно удаляются, изменённые записи восстанавливаются из `before_snapshot`, если это не ломает связи. Откат пишется в аудит и может требовать подтверждения.

### 6.9. Отчёты и дашборды

`GET /api/reports` возвращает доступные шаблоны и ранее созданные отчёты пользователя.

`POST /api/reports` создаёт задание. Тело: `template_code`, `format`, `params`. Форматы: `xls`, `xlsx`, `pdf`, `json`, `png` для графиков. Параметры включают период, вузы, направления, продукты, ответственных, статусы, регионы. Если отчёт лёгкий, он возвращается синхронно. Если тяжёлый, возвращается `202` и идентификатор задания.

Обязательный отчёт по кейсу должен поддерживать колонки: наименование вуза, ИТ-направление, ИТ-продукт, статус работы с вузом, ответственный. Период и фильтры должны применяться к этим данным.

`GET /api/reports/{id}` возвращает статус задания, прогресс, число строк, формат, ошибку и время истечения ссылки.

`GET /api/reports/{id}/download` выдаёт одноразовую короткоживущую ссылку. Перед выдачей проверяются права, статус задания и срок хранения. Скачивание пишется в аудит. Готовые файлы автоудаляются через 7 дней.

`GET /api/dashboards` возвращает дашборды пользователя и общие. `POST /api/dashboards` создаёт дашборд. `PUT /api/dashboards/{id}` обновляет. `POST /api/dashboards/{id}/widgets` добавляет виджет. `DELETE /api/dashboards/{id}/widgets/{widgetId}` удаляет виджет. Данные виджетов должны быть агрегированными и не раскрывать лишние ПДн.

### 6.10. Интеграции

`POST /api/v1/integrations/cms/leads` принимает лиды с сайта. Заголовки: подпись, идентификатор источника, `Idempotency-Key`. Подпись проверяется по HMAC-SHA256. Сырое тело сохраняется в `inbound_messages`. Затем выполняется дедупликация по `source_code` и `external_id`. Создаются контакт и сделка в B2C-воронке, либо лид привязывается к существующей сущности. Ответ должен быть идемпотентным.

Тело лида должно включать минимум: `external_id`, `created_at`, `name`, `contact`, `email`, `phone`, `product_code` или `program_code`, `comment`, `source_url`. Если какие-то поля отсутствуют, контакт помечается как требующий нормализации.

Интеграция с LMS работает через фоновую задачу. Задача периодически вызывает внешний контракт с курсором `updated_since`, сохраняет курсор в `sync_cursors`, обновляет `learning_progress`. При переходе сделки в статус запуска обучения система отправляет событие зачисления через `outbox`.

`GET /api/admin/integrations/sources` возвращает источники. `POST /api/admin/integrations/sources` создаёт источник. `PATCH /api/admin/integrations/sources/{id}` обновляет. `POST /api/admin/integrations/sources/{id}/test` проверяет доступность. `POST /api/admin/integrations/sources/{id}/sync-now` запускает принудительную синхронизацию.

### 6.11. Уведомления

`GET /api/notifications` возвращает уведомления пользователя. Фильтры: `is_read`, `priority`, `entity_type`, `event_code`.

`POST /api/notifications/read` помечает уведомления прочитанными. Тело может содержать список идентификаторов или фильтр.

`GET /api/me/notification-prefs` возвращает настройки пользователя. `PUT /api/me/notification-prefs` обновляет настройки каналов и тихих часов.

Доставка выполняется через очередь. Одно событие может доставляться в несколько каналов. Для каждого канала создаётся отдельная запись в `notification_deliveries`.

### 6.12. Аудит, флаги, настройки

`GET /api/admin/audit` возвращает аудит. Доступ: `ADMIN`, `AUDITOR`, частично `HEAD` по команде. Фильтры: `actor_id`, `entity_type`, `entity_id`, `action`, `result`, `from`, `to`, `request_id`. Экспорт аудита создаёт отдельный отчёт и пишет событие массового экспорта.

`GET /api/admin/feature-flags` возвращает флаги. `PATCH /api/admin/feature-flags/{code}` включает или выключает флаг. Изменение пишется в аудит.

`GET /api/admin/system-settings` возвращает настройки. `PUT /api/admin/system-settings/{key}` изменяет настройку. Секретные значения не возвращаются в открытом виде.

### 6.13. Здоровье и документация

`GET /health/live` проверяет, что процесс жив. `GET /health/ready` проверяет БД, Redis, Keycloak JWKS, SeaweedFS и очередь. `GET /metrics` отдаёт метрики Prometheus.

`GET /api/openapi.json` отдаёт OpenAPI-спецификацию. `GET /api/docs` показывает Swagger UI. Каждая ручка должна иметь схемы запроса и ответа, коды ошибок, требования авторизации, идемпотентность и описание.

## 7. Воронки: что именно нужно посеять

Для кейса нужно посеять не просто «какие-то статусы», а конкретные воронки из `new_spec.md`.

B2B-воронка `b2b_university_v1` должна содержать следующие промежуточные статусы: `identification`, `first_contact`, `qualification`, `meeting_scheduled`, `meeting_held`, `requirements`, `kp_preparation`, `kp_approval`, `legal_approval`, `contract_signing`, `lms_transfer`, `training_launch`, `monitoring`, `closing_prolongation`. Дополнительно создаются терминальные статусы: `won`, `lost`, `parked`.

Переходы должны быть не только вперёд. Для каждого статусного шага нужно предусмотреть возвраты, если это допустимо. Переходы в `lost` требуют `loss_reason_id` и комментарий. Переход в `won` требует сумму и дату. Переход в `parked` требует дату возобновления или причину, а также останавливает SLA.

Для шага `kp_approval` нужно добавить действие `request_signature`, если согласование КП реализуется через ПЭП. Для шага `legal_approval` можно добавить действие запроса подписи или задачи юристу. Для шага `contract_signing` нужно условие `signature_status == signed` или наличие подписанного договора через вложение и административное подтверждение, если ПЭП в демо используется только для внутренних согласований. Для шага `lms_transfer` нужно событие интеграции `LEARNING_TRANSFER_REQUESTED`. Для шага `training_launch` нужно событие интеграции `LEARNING_ENROLLMENT_SENT`. Для шага `monitoring` нужно отображение прогресса из `learning_progress`.

B2C-воронка `b2c_individual_v1` должна содержать статусы: `site_application`, `contact_verification`, `consultation`, `payment_contract`, `lms_enrollment`, `training_completed`. Дополнительно также нужны `won`, `lost`, `parked`.

Статус `site_application` создаётся автоматически из входящего лида сайта. Статус `contact_verification` требует подтверждения контакта. Статус `payment_contract` может требовать договор оферты или оплату. Статус `lms_enrollment` отправляет событие в LMS. Статус `training_completed` может использовать данные `learning_progress`.

## 8. DSL условий и действий переходов

Условия переходов должны быть данными, а не кодом. Бекендер должен реализовать декларативный интерпретатор.

Базовый формат условий:

```json
{
  "all": [
    {"field": "amount", "op": "gt", "value": 0},
    {"field": "custom_fields.contract_number", "op": "not_null"}
  ]
}
```

Можно использовать `any` для логического ИЛИ:

```json
{
  "any": [
    {"field": "signature_status", "op": "eq", "value": "signed"},
    {"field": "attachments.contract", "op": "exists"}
  ]
}
```

Поддерживаемые операторы: `eq`, `neq`, `gt`, `gte`, `lt`, `lte`, `not_null`, `is_null`, `in`, `not_in`, `contains`, `exists`, `date_before`, `date_after`.

Поля, которые можно проверять: `amount`, `currency`, `owner_id`, `organization_id`, `contact_id`, `priority`, `loss_reason_id`, `expected_close_date`, `signature_status`, `custom_fields.*`, `attachments.*`, `tasks.open_count`, `products.count`, `students_planned`. Нельзя разрешать произвольные поля без белого списка, иначе конструктор станет дырой безопасности.

Действия переходов хранятся массивом. Пример действия создания задачи:

```json
{
  "type": "create_task",
  "title": "Подготовить договор",
  "assignee_role": "KAM",
  "due_days": 3,
  "priority": "high"
}
```

Пример уведомления:

```json
{
  "type": "notify",
  "event_code": "DEAL_STATUS_CHANGED",
  "channels": ["in_app", "email"],
  "recipients": ["owner", "manager"]
}
```

Пример запроса подписи:

```json
{
  "type": "request_signature",
  "template": "kp_approval",
  "signers": [
    {"role": "HEAD"},
    {"contact_role": "decision_maker"}
  ],
  "order": "sequential",
  "deadline_days": 7,
  "on_rejected": "previous_status",
  "on_expired": "notify_initiator"
}
```

После появления действия `request_signature` сделка должна получить `signature_status = pending` и `active_signature_document_id`. Переходы, которые требуют подписи, используют условие `{"field": "signature_status", "op": "eq", "value": "signed"}`.

Если подпись отклонена, сделка возвращается на предыдущий статус или на статус, указанный в правиле `on_rejected`. В историю пишется `reason = 'signature_rejected'`, в комментарии сохраняется причина отказа, инициатор получает уведомление.

## 9. Файлы: как должен работать полный цикл

Последовательность загрузки обязательна такая: сначала клиент вызывает `POST /api/files/upload-intent`, затем загружает файл напрямую в SeaweedFS по presigned URL, затем вызывает `POST /api/files/{id}/commit`. Нельзя гнать тело файла через API как основную загрузку.

На этапе `upload-intent` проверяется имя файла, размер, MIME-тип, категория и права. Если тип не разрешён, возвращается `415 CRM-1401`. Если размер превышен, возвращается `413 CRM-1402`. Если пользователь не имеет права привязать файл к сделке или организации, возвращается `403 CRM-1102`.

На этапе `commit` сервер проверяет, что объект реально существует в бакете. Затем сверяются размер и хэш. Если хэш не совпадает, запись помечается ошибочной. Далее запускается антивирусная проверка. До завершения проверки файл нельзя использовать в переходе как обязательное вложение, если политика безопасности требует только `ready`-файлы.

При скачивании сервер не отдаёт файл напрямую. Он выдаёт одноразовую короткоживущую ссылку. Перед выдачей ссылки проверяется право доступа к родительской сущности. Если файл содержит ПДн, доступ должен быть дополнительно ограничен, а факт скачивания пишется в аудит.

Файлы, созданные подписью, протоколы, штампы и акты уничтожения должны храниться в отдельных бакетах с ограничением перезаписи и удаления. Для подписных документов нужно использовать WORM-подобную политику: приложение может читать и создавать объекты, но не может изменять или удалять их. Удаление разрешается только отдельной ретеншен-задаче по истечении срока хранения.

## 10. Импорт: как сделать его понятным и безопасным

Импорт должен состоять из пяти фаз: загрузка, разбор и профилирование, маппинг, сухой прогон, применение. Откат является отдельной операцией после применения.

Загрузка принимает только `xls` и `xlsx`. Формат определяется по сигнатуре. Для `xlsx` используется `openpyxl` в режиме `read_only`. Для `xls` используется `xlrd`. Если файл повреждён, возвращается `400 CRM-1801` с понятной причиной. Если есть признаки формул, макросов или подозрительных команд, файл блокируется.

Маппинг должен поддерживать автоподбор по именам колонок. Например, «Наименование», «Название ВУЗа», «ВУЗ» должны предлагаться к `organizations.name`. «ИНН» к `organizations.inn`. «Ответственный» к `deals.owner_id`. «Статус по передачи» к статусу сделки через словарь значений. Маппинг сохраняется как пресет и подставляется при повторной загрузке похожего файла.

Сухой прогон обязан вернуть три категории: корректные строки, предупреждения и ошибки. Для ошибок формируется отдельный файл, где к исходным данным добавляется колонка с причиной. Без сухого прогона применять импорт нельзя, если число ошибок выше порога.

Применение должно быть батчевым. Ошибочные строки не роняют весь импорт. Для изменённых записей сохраняется `before_snapshot`. После применения создаётся отчёт и становится доступен откат.

Откат должен работать по `import_job_id`. Созданные импортом записи помечаются или безопасно удаляются. Изменённые записи восстанавливаются из снапшота. Если сущность уже связана с критичными данными, например со сделками, подписями или историей, откат по этой строке может быть заблокирован, и это должно быть явно показано пользователю.

## 11. Отчёты: как выполнить требования кейса и не положить систему

Отчёты нельзя делать только синхронными. Требование 10 параллельных отчётов реализуется очередью и семафором. Лёгкие отчёты можно отдавать быстро, тяжёлые уходят в фон.

Лёгким считается отчёт, который выполняется быстрее двух секунд и возвращает меньше 1000 строк. Такой отчёт можно синхронно вернуть как файл. Тяжёлый отчёт возвращает `202` и `report_job_id`.

Параллельность генерации не должна быть ниже 10. Лучше выставить настройку `REPORTS_MAX_CONCURRENT` по умолчанию 12, но ниже 10 не снижать. Если превышен лимит, возвращается `429 CRM-1601`.

Каждая генерация отчёта пишется в аудит как `REPORT_EXPORTED`. В аудите указываются параметры, число строк, формат, категории данных и пользователь. Если отчёт содержит ПДн, доступ должен проверяться по скоупу, а для больших массивов ПДн можно требовать внутреннее согласование ПЭП.

Файлы результатов хранятся в отдельном бакете. Ссылка на результат короткоживущая и одноразовая. Срок хранения результата — 7 дней. После этого файл удаляется фоновой задачей.

Графики выгружаются серверно, например через matplotlib. Нельзя делать скриншот браузера. Для кейса нужно поддержать визуализацию в `png` и `pdf`. Для табличной части — `xls`, `xlsx`, `pdf`, `json`.

## 12. Интеграции: как не потерять события

Все входящие сообщения должны сохраняться сырыми в `inbound_messages` до обработки. Если парсер упал, сообщение можно переобработать. Дедупликация делается по `source_code` и `external_id`.

Для входящего вебхука сайта нужно проверять подпись. Если подпись неверна, возвращается `401 CRM-1701`, сообщение помечается как невалидное, но сырой запрос сохраняется. Если подпись верна и сообщение новое, создаётся контакт и сделка в B2C-воронке. Если контакт уже существует, лид привязывается к существующему контакту.

Все исходящие события должны идти через `outbox_events`. В одной транзакции с бизнес-изменением создаётся событие. Отдельный воркер читает события и доставляет их с повторами. Повторы должны быть экспоненциальными: 1 секунда, 5 секунд, 30 секунд, 5 минут, 30 минут, 2 часа. После нескольких неудач событие попадает в `dead_letter`, и администратор получает алерт.

Нужно завести базовые типы исходящих событий: `DEAL_CREATED`, `DEAL_STATUS_CHANGED`, `DEAL_OWNER_CHANGED`, `DEAL_CLOSED`, `LEARNING_ENROLLMENT_SENT`, `DOCUMENT_SIGNED`, `SIGNATURE_REJECTED`, `ERASURE_REQUESTED`. Для каждого события должна быть понятная схема в OpenAPI.

Для Bitrix-коннектора реализуется отдельный контейнер. Ядро не должно знать про Bitrix. Коннектор читает наш outbox и пишет в `external_refs`. Конфликты решаются по правилу last-write-wins, но все расхождения пишутся в журнал. Если коннектор выключить, система должна продолжать работать.

## 13. ПЭП: как реализовать юридически значимую подпись

ПЭП нельзя делать как простое «ввести код и поставить галочку». Система должна фиксировать доказательство: кто подписал, когда, каким способом, с какого устройства, какой документ, был ли ознакомлен, было ли согласие на ЭДО, какой хэш документа, какой источник времени.

Документ на подпись создаётся из шаблона или загруженного PDF. Для него считается `content_hash = sha256(pdf_bytes)`. Файл сохраняется в бакет, где приложение не может его перезаписать или удалить. Все дальнейшие проверки опираются на хэш, а не на имя файла.

Перед отправкой внешнего подписанта проверяется `edm_agreements`. Если действующего соглашения нет, документ получает статус `blocked_no_agreement`, а инициатор получает инструкцию оформить соглашение. Нельзя подписывать внешние документы без действующего соглашения.

Для внешнего подписанта создаётся одноразовая ссылка. В базе хранится только `sha256(token)`, сам токен не хранится. Ссылка имеет TTL по умолчанию 7 дней. Открытие страницы фиксируется: время, IP, User-Agent. Статус запроса становится `viewed`. Без фиксации ознакомления подпись слабая.

Код подтверждения генерируется как 6-значный код. Хранится только `bcrypt(code)` с солью. Срок жизни кода — 5 минут. Максимум три попытки. Отправка кода ограничена по частоте: не чаще одного раза в 60 секунд и не более пяти кодов на запрос. Канал доставки берётся только из заранее верифицированных контактов. Менять канал в момент подписания нельзя.

При подписании сервер повторно пересчитывает хэш файла. Если хэш не совпадает, возвращается `409 CRM-1502`, подпись не ставится, создаётся событие безопасности. Если хэш совпадает и код верен, создаётся запись в `signatures`. Она включает метод, отображение подписанта, подпись, алгоритм, `evidence`, время, источник времени, дрейф времени, IP, User-Agent, хэш документа, предыдущий хэш и собственный хэш.

`signature_value` считается как `HMAC-SHA256(server_secret, content_hash || signer_id || signed_at || nonce)`. Это метка целостности записи, а не криптографическая УКЭП. В документации это нужно писать честно.

После подписания асинхронно генерируются протокол подписания, штамп на последней странице, JSON-манифест и уведомления. Событие `DOCUMENT_SIGNED` попадает в `outbox_events`. Сделка может автоматически перейти на следующий статус, если в действиях перехода задано `on_all_signed`.

Проверка подписи должна быть публичной. `GET /public/verify/{signature_id}` показывает только факт подписи, ФИО или снимок подписанта, дату, хэш и статус. `POST /api/signatures/verify` принимает файл и сверяет его хэш с сохранённым. Это можно показать на демо за 20 секунд.

При смене пароля все незавершённые запросы подписи пользователя аннулируются со статусом `void` и причиной `credentials_changed`. Уже поставленные подписи не трогаются. При компрометации или сбросе пароля незавершённые запросы аннулируются безусловно, подписи за последние 24 часа могут помечаться `is_disputed`, создаётся событие `SIGNATURE_KEY_COMPROMISED`.

При обезличивании пользователя подписи не обезличиваются. В `data_erasure_requests` автоматически появляется блокер `has_signatures`. Основание — подпись без идентификации подписанта теряет смысл, а документы нужны для исполнения договора и защиты прав оператора.

## 14. ЕГРЮЛ и автоподстановка по ИНН

Автоподстановка должна работать в закрытом контуре. Поэтому основной провайдер — локальный реестр ЕГРЮЛ, а не внешний сервис. Внешние провайдеры могут быть только опциональными и выключенными по умолчанию.

Цепочка провайдеров должна быть такой: `LocalRegistryProvider`, затем `InternalCacheProvider`, затем опциональный внешний провайдер, если включён флаг `external_org_lookup`, затем `MockProvider` для тестов. Порядок цепочки задаётся в `system_settings`.

Эндпоинт `GET /api/org-lookup/suggest` принимает `q` и `limit`. Он ограничен по частоте, например 30 запросов в минуту на пользователя. Каждый запрос пишется в `org_lookup_log`. В ответе возвращаются краткое наименование, ИНН, город, статус. Ликвидированные организации показываются с предупреждением.

Эндпоинт `GET /api/org-lookup/inn/{inn}` проверяет контрольную сумму ИНН и возвращает полные данные из локального реестра. Эндпоинт `POST /api/org-lookup/validate` проверяет ИНН, ОГРН, ОГРНИП или КПП. Валидация должна выполняться на бэкенде обязательно, даже если фронтенд уже проверил.

При создании организации по ИНН найденная организация заполняет поля, сохраняется `registry_snapshot`, `verified_source`, `verified_at`, `registry_version_id`. Поля, изменённые пользователем вручную, отмечаются в `manual_overrides` и не затираются при обновлении из реестра.

Фоновая задача сверки проходит по организациям с ИНН и сравнивает данные с актуальным реестром. При расхождениях изменения не применяются автоматически, а пишутся в `requisites_drift`. Ответственному приходит уведомление. В карточке организации показывается баннер с дифом и кнопками принять или отклонить.

Если статус организации меняется на ликвидацию и есть активные сделки, создаётся критичное уведомление, задача юристу и флаг в карточке. Это важный бизнес-эффект: система ловит риск подписания договора с ликвидируемым юрлицом.

## 15. Фоновые задачи и планировщик

Для бекендера должен быть явный список фоновых задач. Каждая задача имеет имя, входные параметры, результат, политику повторов, таймаут и метрики.

`files.scan_file` проверяет файл антивирусом. Запускается после `commit`. При обнаружении малвари меняет статус файла и создаёт событие безопасности.

`imports.apply` применяет импорт батчами. Запускается после `POST /api/imports/{id}/apply`. Пишет прогресс и ошибки строк.

`imports.rollback` откатывает импорт. Запускается после `POST /api/imports/{id}/rollback`. Восстанавливает снапшоты и помечает созданные записи.

`reports.generate` генерирует отчёт. Запускается после создания `report_jobs`. Имеет семафор на 10–12 параллельных задач. После генерации пишет `REPORT_EXPORTED`.

`registry.import` импортирует выгрузку ЕГРЮЛ. Запускается после `POST /api/admin/registry/import`. Парсит XML потоково, вставляет батчами, обновляет версии реестра.

`registry.reconcile` сверяет организации с реестром. Запускается по расписанию раз в 30 дней или после импорта новой версии. Пишет `requisites_drift` и уведомления.

`workflow.status_mapping` переносит сделки при архивировании статуса. Запускается после `POST /api/workflows/{id}/statuses/{sid}/archive`. Работает батчами, пишет историю и системные комментарии.

`notifications.dispatch` отправляет уведомления по каналам. Запускается после создания уведомлений или по событиям. Повторяет доставку при временных ошибках.

`signature.send_notifications` отправляет напоминания и ссылки подписантам. Запускается по событию создания запроса и по расписанию напоминаний.

`signature.expire_deadlines` помечает просроченные запросы подписи. Запускается каждые 15 минут. Создаёт уведомления инициаторам и возвращает сделки по правилам отказа или просрочки.

`signature.clean_otp` очищает старые OTP-записи. Запускается ежедневно. Удаляет записи старше 30 дней, потому что доказательства хранятся в `signatures.evidence`, а не в кодах.

`sla.scan` проверяет просроченные сделки. Запускается каждые 15 минут. Меняет `sla_state`, создаёт уведомления и эскалации.

`lms.sync_progress` забирает прогресс из LMS. Запускается каждые 30 минут. Обновляет `learning_progress` и `sync_cursors`.

`outbox.deliver` доставляет исходящие события. Запускается постоянно. Повторяет ошибки с экспоненциальной задержкой, переводит в `dead_letter` после лимита.

`retention.cleanup_files` удаляет файлы с нулевым `refcount` и истёкшим сроком хранения. Запускается ежедневно.

`erasure.execute` выполняет обезличивание или удаление по подтверждённым запросам. Запускается по дедлайну или вручную. Работает по шагам с чекпоинтами.

`keycloak.sync_users` сверяет пользователей с Keycloak. Запускается ежедневно. Ловит события, которые могли быть пропущены, например блокировку или удаление.

`cache.refresh_materialized` обновляет материализованные представления для дашбордов. Запускается по расписанию. Использует `REFRESH CONCURRENTLY`, если есть уникальные индексы.

## 16. Кэш: какие ключи использовать

Кэш нужен не просто для скорости, а для выполнения требования по отклику. Но кэш не должен становиться источником правды.

`cache:deal:{id}:v{version}` хранит собранную карточку сделки. TTL 10 минут. Инвалидация через версию: при обновлении сделки `version` увеличивается, старый ключ просто не читается.

`cache:catalog:{type}:{hash}` хранит справочники. TTL 1 час. Инвалидация явная при изменении справочника.

`cache:wf:{workflow_id}` хранит опубликованный граф воронки. TTL 1 час. Инвалидация при публикации.

`cache:perm:{user_id}` хранит развёрнутый набор прав. TTL 5 минут. Инвалидация при смене роли, команды, блокировке, выходе, обезличивании.

`recent:{user_id}` хранит последние 20 открытых сущностей. Это требование кейса про кэш действий пользователя. Используется Redis ZSET.

`lock:{resource}` хранит короткие локи. Например, `lock:deal:{id}:transition` для защиты от двойного перехода.

`idem:{key}` хранит идемпотентные ответы. TTL 24 часа.

`rl:{ip}:{route}` хранит счётчики rate-limit. Например, для публичных страниц подписания и автоподстановки.

Если Redis недоступен, система должна деградировать предсказуемо. Для чтения можно идти в БД медленнее. Для операций с локами, идемпотентностью и сессиями лучше возвращать ошибку, чем рисковать двойным действием.

## 19. Требования к кейсовым полям и отчётам

Кейс требует каталоги с конкретными полями. Чтобы не ломать архитектуру `new_spec`, их нужно разложить так.

«Название ВУЗа» хранится в `organizations.name`.

«Вендор» хранится как пользовательское поле продукта или организации, либо как связанная организация с типом `company`, если вендор ведётся как контрагент. Отдельная таблица `vendors` не нужна.

«ПО» хранится в `products`, если ПО является продуктом, либо в пользовательском поле `software_name` для сделки или организации.

«Номер договора» хранится в `deals.custom_fields.contract_number`.

«Подписание лицензии» хранится как признак в `deals.custom_fields.license_signed`, плюс файлы категории `license` или `contract`, плюс подпись ПЭП, если она используется.

«Срок действия лицензии» хранится в `deals.custom_fields.license_valid_until` или `products.valid_to`, если срок относится к продукту. Если срок лицензии нужно отслеживать, создаётся фоновая задача уведомлений о приближающемся истечении.

«Статус по передаче» маппится на статус сделки в опубликованной воронке. Для импорта используется словарь значений.

«ФИО Менеджера» маппится на `deals.owner_id` через справочник пользователей.

«Ответственные от ВУЗа» хранятся как `contacts`, связанные с организацией, и при необходимости как участники сделки.

«Комментарий» сохраняется в `deal_comments` или `organizations.custom_fields.comment`, если комментарий относится к организации, а не к конкретной сделке.

Отчёт по кейсу должен уметь фильтровать данные за период по вузам, ИТ-направлениям, ИТ-продуктам, программам и ответственным. В интерфейсе пользователю это может называться «ИТ-программа», но в модели это может быть продуктом с признаком программы. Отчёт должен поддерживать колонки: наименование вуза, ИТ-направление, ИТ-продукт, статус работы с вузом, ответственный.

Если заказчику принципиально нужно отдельное поле «ИТ-программа», оно реализуется через `custom_field_defs` или `products.custom_fields.product_kind = 'program'`, а не через отдельную таблицу `it_programs`, если только команда осознанно не решит расширить модель и не задокументирует это.

## 20. Обновлённые спринты для бекендера

### Спринт 0 — каркас

Задачи: структура модулей, конфигурация, миграции, обработка ошибок, `request_id`, RFC 7807, Keycloak-валидация JWT, health-checks, метрики, OpenAPI, базовые таблицы `feature_flags`, `system_settings`, `idempotency_keys`, заготовка аудита.

Готово, когда чистое окружение поднимается одной командой без интернета, логин через Keycloak работает, `/api/me` возвращает профиль, ошибки имеют единый формат, `request_id` проходит через логи и ответ.

### Спринт 1 — identity и аудит

Задачи: таблицы пользователей, команд, согласий, событий безопасности, запросов удаления. Ручки `/api/me`, `/api/me/sessions`, `/api/me/password`, `/api/me/consent`, админские ручки пользователей. Роли, скоупы, `perm_epoch`. Аудит пишется в транзакции.

Готово, когда пользователь входит, роли работают, смена пароля завершает сессии и аннулирует незавершённые подписи, блокировка и увольнение работают, каждое действие видно в аудите.

### Спринт 2 — воронки

Задачи: таблицы `workflows`, `workflow_statuses`, `workflow_transitions`, `sla_rules`, `status_mapping_jobs`. Ручки создания, редактирования, валидации, публикации, архивирования статуса, предпросмотра влияния. Сиды B2B и B2C воронок.

Готово, когда администратор может собрать 14-шаговую воронку без кода, публикация блокирует некорректный граф, архивирование статуса с живыми сделками работает только через маппинг.

### Спринт 3 — сделки

Задачи: таблицы сделок, истории, событий, участников, продуктов, комментариев, задач. Ручки списка, создания, карточки, обновления, переходов, доступных переходов, истории, комментариев, назначения ответственного. Оптимистичная блокировка, аудит, скоупы.

Готово, когда сделка проходит обе воронки, переходы проверяют условия и права, комментарии сохраняют ревизии, история не редактируется, чужие сделки недоступны.

### Спринт 4 — каталоги, организации, контакты, файлы

Задачи: таблицы организаций, контактов, каналов, регионов, продуктов, направлений, причин отказа, праздников, пользовательских полей. Ручки каталогов, контактов с `reveal`, организаций с дедупликацией по ИНН. Файлы через presigned URL, антивирус, вложения.

Готово, когда организация создаётся по ИНН, дубль по ИНН блокируется, контакты маскируются и раскрываются с аудитом, файлы загружаются безопасно и не удаляются при ссылках.

### Спринт 5 — ЕГРЮЛ и импорт

Задачи: таблицы ЕГРЮЛ, версий реестра, журнала орг-лук, импортных заданий, строк и пресетов. Ручки автоподстановки, валидации ИНН, импорта, маппинга, сухого прогона, применения, отката. Фоновая задача импорта реестра и сверки дрейфа.

Готово, когда импорт 5000 строк проходит без падения, битые файлы обрабатываются, ошибки выгружаются, откат работает, автоподстановка работает офлайн, ликвидируемые организации подсвечиваются.

### Спринт 6 — отчёты и дашборды

Задачи: таблицы шаблонов, заданий, дашбордов и виджетов. Ручки создания, статуса, скачивания, дашбордов. Очередь на 10+ параллельных отчётов. Форматы `xls`, `xlsx`, `pdf`, `json`, `png`. Аудит выгрузок.

Готово, когда 10 параллельных отчётов не роняют интерфейс, отчёт по кейсу содержит нужные колонки, ссылки одноразовые, файлы автоудаляются, выгрузки пишутся в аудит.

### Спринт 7 — интеграции

Задачи: таблицы источников, входящих сообщений, outbox, внешних идентификаторов, курсоров, прогресса. Ручка входящего вебхука, админка источников, фоновые задачи синхронизации и доставки. Мок-сервисы.

Готово, когда лид с сайта создаёт B2C-сделку, прогресс из LMS появляется в сделке, исходящие события доставляются после сбоя, дубли не создаются.

### Спринт 8 — ПЭП

Задачи: таблицы соглашений, шаблонов, документов, запросов, кодов, подписей. Ручки создания, отправки, ознакомления, кода, подписания, отказа, аннулирования, проверки. Фоновые задачи напоминаний, просрочки и очистки кодов.

Готово, когда внутренний и внешний подписант могут подписать документ, отсутствие соглашения блокирует внешнюю подпись, изменение файла обнаруживается, публичная проверка показывает статус подписи без авторизации.

### Спринт 9 — администрирование, 152-ФЗ и документация

Задачи: доработка управления пользователями, offboarding, erasure-запросы, обезличивание, акты уничтожения, аудит, флаги, настройки, документация.

Готово, когда увольнение передаёт дела без потери истории, запрос субъекта корректно блокируется или обезличивается, акт формируется и подписывается, админские операции требуют подтверждения и пишутся в аудит.

### Спринт 10 — нагрузочное тестирование и сдача

Задачи: нагрузочные тесты на 50 пользователей, 10 параллельных отчётов, переходы и комментарии под нагрузкой. Индексы, кэш, устранение N+1. Проверка аудита. Развёртывание на чистой Ubuntu. Демо-сценарий дважды подряд.

Готово, когда окружение разворачивается по инструкции незнакомым человеком, демо проходит без ручного вмешательства, показатели отклика и параллельных отчётов соответствуют требованиям, документация встроена в платформу.

## 21. Что бекендер должен считать Definition of Done для любой ручки

Для каждой новой ручки бекендер обязан сделать не только код, но и следующие вещи.

Ручка описана в OpenAPI: метод, путь, параметры, тело запроса, тело ответа, коды ошибок, роль, идемпотентность, если нужна, и пример.

Проверка прав реализована на уровне маршрута, объекта и списка. Нельзя полагаться только на скрытие кнопки во фронтенде.

Все изменения пишутся в аудит в той же транзакции. Если действие меняет данные, но не пишет аудит, задача не считается готовой.

Все ошибки имеют код из каталога. Нельзя возвращать голый 500 с произвольным текстом или 422 без понятного поля.

Списки используют курсорную пагинацию и скоуп. Нельзя возвращать чужие данные из-за забытого фильтра.

Если сущность обновляется, поддерживаются `If-Match` и `version`. Если сущность создаётся и может быть задублирована, поддерживается `Idempotency-Key`.

Если действие тяжёлое, оно уходит в очередь. Синхронная ручка не должна блокировать воркер на минуты.

Если действие связано с файлами, подписями, ПДн, интеграциями или удалением, должны быть явные статусы, события безопасности и понятные ошибки.

Если действие влияет на фронтенд, контракт должен быть согласован через OpenAPI, а не через устную договорённость.

## 22. Минимальный чек-лист перед сдачей

Перед сдачей нужно пройтись по следующему списку.

Развёртка поднимается одной командой на чистой машине без внешнего интернета.

Логин через Keycloak работает, сессии хранятся в Redis, браузер не получает токены в открытом виде.

Пользователь видит только свои данные, руководитель видит данные команды, администратор видит всё.

Сделка создаётся, проходит 14 шагов B2B и 6 шагов B2C, закрывается в `won`, `lost` и `parked`.

Переход по статусу занимает не более целевого времени, проверяет права, условия, комментарий, файлы и подпись.

Воронку можно изменить без правки кода. Публикация валидирует граф. Архивирование статуса переносит сделки.

Импорт принимает `xls` и `xlsx`, поддерживает маппинг, сухой прогон, отчёт об ошибках и откат.

Отчёты строятся за выбранный период, поддерживают фильтры по вузам, направлениям, продуктам и ответственным, выгружаются в `xls`, `xlsx`, `pdf`, `json`, графики в `png` или `pdf`.

10 параллельных отчётов не роняют интерфейс.

Файлы загружаются в разрешённых форматах, проверяются по размеру, типу и антивирусом.

ПЭП работает: документ отправляется, подписант знакомится, получает код, подписывает, проверка подписи публично доступна.

Автоподстановка по ИНН работает офлайн, дубли по ИНН не создаются, ликвидируемые организации подсвечиваются.

Интеграции принимают лиды с сайта и прогресс из LMS, события уходят через outbox.

Аудит неизменяемый, каждое изменение данных фиксируется, чувствительные поля маскируются.

Обезличивание и удаление работают через запросы, блокеры и акты. Аудит не удаляется.

Документация администратора и пользователя встроена, содержит скриншоты, коды ошибок, инструкции по развёртыванию и меры по 152-ФЗ.

Если всё это выполнено, бекенд можно считать готовым к интеграции с фронтендом и демонстрации.
