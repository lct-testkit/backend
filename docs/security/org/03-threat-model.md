# Модель угроз безопасности персональных данных

Основание: постановление Правительства РФ № 1119 «Об утверждении требований к защите
персональных данных...», методика оценки угроз безопасности информации ФСТЭК России (2021).
Черновик — идентификаторы угроз БДУ ФСТЭК не сверялись (нужен специалист по защите
информации), названия мер — по структуре приказа ФСТЭК № 117 (см.
[матрицу мер](../measures-matrix.md), B6-1).

## Границы информационной системы

CRM-платформа (backend FastAPI-монолит + Keycloak + PostgreSQL + Redis + SeaweedFS),
развёрнутая в выделенном контуре. Внешние границы: вход через Keycloak (OIDC), публичная
ссылка на подписание документа без аутентификации (B7-3), входящие вебхуки интеграций
(HMAC-подпись, `app/modules/integration/security.py`).

## Нарушители

| Тип | Описание | Потенциал |
| --- | --- | --- |
| Внешний неавторизованный | не имеет учётной записи, пытается подобрать пароль/перебрать токен | низкий-средний |
| Внешний с украденными учётными данными | получил пароль/сессионный токен законного пользователя | средний |
| Внутренний (сотрудник оператора) | имеет легитимный доступ в пределах своей роли, превышает полномочия | средний |
| Привилегированный внутренний (ADMIN) | имеет полный доступ к системе | высокий (компрометация такой учётки — самый тяжёлый случай) |
| Внешний подписант (контакт) | имеет одноразовую ссылку/токен на подписание конкретного документа | низкий (ограничен возможностями публичной ручки) |

## Актуальные угрозы

| № | Угроза | Объект | Мера защиты (где в коде/матрице) |
| --- | --- | --- | --- |
| 1 | Подбор пароля сотрудника | учётные данные | Keycloak brute-force protection + опрос событий (B6-3) |
| 2 | Кража/повторное использование сессии (session hijacking, refresh token reuse) | сессия пользователя | ротация refresh-токенов, `SESSION_HIJACK_SUSPECT` (B6-11) |
| 3 | Загрузка вредоносного файла под видом документа | файловое хранилище, устройства пользователей | антивирусная проверка ClamAV, карантин (B6-4/B6-5) |
| 4 | Расширение файла не соответствует содержимому (`.doc` на деле `.xls`, zip под `.docx`) | целостность файлов | глубокая проверка по содержимому (B2-9) |
| 5 | Утечка ПДн через дамп базы для разработки/тестового стенда | ПДн всех субъектов | обезличенный дамп (B6-13) |
| 6 | Компрометация ключа `AUDIT_HMAC_KEY` → подмена журнала аудита без обнаружения | журнал аудита | обязательный ключ в prod, цепочка хэшей (B6-8) |
| 7 | Подмена/удаление записи журнала аудита или подписи | журнал аудита, подписи | триггеры неизменяемости БД, цепочка хэшей с проверкой целостности |
| 8 | Инсайдер с правом раскрытия ПДн (`contact:reveal`/`org:reveal`) злоупотребляет доступом | ПДн контактов | аудит каждого раскрытия (`PII_REVEALED`), ролевой доступ |
| 9 | Перехват одноразового кода (OTP) при подписании документа | ПЭП, юридическая значимость подписи | лимит попыток, лимит отправок в минуту, событие `SIGNATURE_OTP_FAILED` (B7-5) |
| 10 | Использование уязвимой зависимости/образа контейнера | вся система | pip-audit, Trivy в CI (B6-15) |
| 11 | Утрата или компрометация резервной копии с ПДн | ПДн всех субъектов | шифрование тома хранения (спринт D), ротация копий (не в этом каталоге) |
| 12 | Утечка через логи приложения (пароль/токен/ПДн попадает в лог) | ПДн, учётные данные | маскирование секретов и ПДн в структурных логах, тест `test_request_log_redaction.py` |
| 13 | Инцидент безопасности выявлен, но не зафиксирован и не доведён до регулятора в срок | соответствие 152-ФЗ ст. 21 ч. 3.1 | реестр инцидентов, сроки РКН 24/72 ч (B6-12) |
| 14 | Утечка/искажение персональных данных слушателя при передаче в учебную организацию/LMS | ПДн слушателя | шифрование профиля слушателя при хранении (B6-7); канал передачи — за пределами backend |

## Вывод об уровне защищённости

Постановление № 1119 определяет уровень защищённости (УЗ) исходя из типа актуальных угроз,
категории ПДн (специальные/биометрические/общедоступные/иные) и количества субъектов.
Платформа обрабатывает ПДн сотрудников и контактов (иные категории ПДн, не специальные и не
биометрические) в объёме нескольких тысяч субъектов (сотрудники + контакты вузов +
слушатели).

- Если принимаются только угрозы **2-го типа** (связанные с недекларированными
  возможностями в системном программном обеспечении) — требуется **УЗ-3**.
- Если актуальны угрозы **3-го типа** (не связанные с НДВ в системном и прикладном ПО, но
  актуальные для прикладного ПО) — требуется **УЗ-4**.

**Это предположение, не завершённый расчёт**: выбор типа угроз делает комиссия оператора
(специалист по защите информации), не авторы этого спринта. До решения комиссии в
`.github/docs/ACCOMPANYING-DOCUMENTATION.md` зафиксировано «УЗ-3 предположительно» — этот
документ эту формулировку не меняет, только явно показывает, от чего она зависит.

## Открытый вопрос владельцу/организаторам

операционная система для заявленного уровня защищённости?
