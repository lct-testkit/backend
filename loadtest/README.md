# Нагрузочное тестирование

Проверяет new_spec §0 (критерий успеха №1): «p95 времени ответа API на
операции «переход по статусу» и «добавление комментария» ≤ 300 мс при
50 RPS». Соответствует §9 шагу 10 порядка реализации.

## Автоматический гейт (CI)

`bash loadtest/run_ci.sh` — то же, что ниже, одной командой и с проверкой SLO: первый вход демо-КАМа (создаёт
пользователя и принимает согласие на ПДн — без этого мутирующие ручки отвечают `403 CRM-1105`), `provision.py`,
затем оба сценария при **фиксированных 50 RPS** (`LOADTEST_RPS_PER_USER=1` при 50 пользователях) и
`assert_slo.py`: p95 ≤ 300 мс, ошибок ≤ 1%, достигнутый RPS ≥ 90% цели (иначе гейт «зеленел» бы вхолостую).
В GitHub Actions это `.github/workflows/loadtest.yml` (ночью, вручную, PR с меткой `perf`).

Виртуальные пользователи **делятся одним токеном** (`_shared_token`): 50 одновременных password-grant'ов от одного
демо-КАМа срабатывают как брутфорс, Keycloak временно блокирует пользователя (`user_temporarily_disabled`) и прогон
измеряет защиту IdP, а не API. Параметры — переменные `LOADTEST_*` в шапке `run_ci.sh`.

## Запуск

```bash
# 1. Стек поднят (docker compose up -d), кому нужны реальные реплики —
#    масштабировать api заранее (см. «Реплики» ниже).

# 2. Провижининг тестовых сделок (хост, не контейнер — pip install .[dev]
#    в локальном venv, DATABASE_URL к опубликованному порту Postgres):
python loadtest/provision.py --count 4000 --comment-pool-size 100

# 3. Прогон (локально, requires `pip install -e .[dev]` в venv):
locust -f loadtest/locustfile_transition.py --headless \
    -u 50 -r 25 -t 60s --host=http://localhost:8080 \
    --csv=loadtest/results/transition

locust -f loadtest/locustfile_comment.py --headless \
    -u 50 -r 25 -t 60s --host=http://localhost:8080 \
    --csv=loadtest/results/comment
```

Аутентификация — прямой grant Keycloak (`kam.ivanov`, демо-КАМ из
`deploy/keycloak/realm-crm.json`; пароль по умолчанию в locustfile — тот же, что в realm),
переменные `LOADTEST_*` в обоих locustfile переопределяют пользователя/URL/пароль при
необходимости. Запросы идут с `Authorization: Bearer`, минуя cookie-сессию и CSRF-токен: это
работает на профилях `demo`/`dev`, а в `prod` Bearer принимается только от роли INTEGRATION
(подробнее — в шапке `locustfile_transition.py`), поэтому гейт гоняют на `APP_PROFILE=demo`.

## Результаты (2026-09-18, эта сессия)

Стек — docker compose на одной машине (тот же хост, что запускает Locust:
клиент и сервер конкурируют за CPU/IO одного сокета, не выделенный
нагрузочный стенд). `api` масштабирован на 3 реплики (`docker compose up -d
--scale api=3`) — единственная поддерживаемая стратегия масштабирования
по конструкции: `UVICORN_WORKERS=1` внутри контейнера намеренно (реестр
Prometheus живёт в памяти процесса, см. комментарий в docker-compose.yml),
Caddy уже сконфигурирован под это (`dynamic a` DNS-апстрим + `least_conn`,
см. `deploy/Caddyfile`) — просто ещё не было проверено вживую до этого
спринта.

| Операция | Requests | Failures | Достигнутый RPS | p50 | p95 | p99 | Критерий (p95≤300мс) |
|---|---|---|---|---|---|---|---|
| `POST /api/deals/{id}/transition` | 2037 | 0 | 34.4 | 52 мс | **79 мс** | 100 мс | ✅ с запасом ~3.8× |
| `POST /api/deals/{id}/comments` | 3533 | 0 | **59.7** | 31 мс | **49 мс** | 68 мс | ✅ с запасом ~6× |

**Честная оговорка по RPS.** `comments` превысил целевые 50 RPS без
проблем. `transition` уперся в ~34-37 RPS даже на 3 репликах (на 1 реплике
— ~27-29 RPS) — не хватило capacity именно этой sandbox-машины разделить
между 3 процессами uvicorn, Postgres, Redis, Keycloak и самим Locust
одновременно, а не архитектурный потолок: добавление реплик уверенно
подняло и RPS (27→34), и снизило p95 (100→79 мс) — тренд в правильную
сторону, не намёк на скрытый барьер около 50. На выделенном
нагрузочном стенде (или тем более в проде — там же не будет самого
Locust на той же машине) есть все основания ожидать полных 50 RPS без
ухудшения p95: сам API не показал никакой деградации задержки при росте
конкурентности, только рост throughput.

**Первый прогон** (до фиксов, не в таблице выше) поймал два реальных
методологических бага, оба исправлены до финального прогона: (1) ни один
locustfile не задавал `wait_time` — Locust 2.x без явного значения ждёт
между задачами по умолчанию, из-за чего 50 «пользователей» держали
реальный RPS втрое ниже целевого; добавлен `wait_time = constant(0)` в
оба файла. (2) 74 сделки из первого прогона `transition` словили честный
`409 Version Conflict` — фоновый SLA-скан воркера (см. `crm/tasks.py`,
крутится каждые 15-30 с) успел тронуть версию части сделок в промежутке
между провижинингом и прогоном; не баг приложения (оптимistic locking
сработал ровно так, как задуман new_spec §3.5), просто `provision.py`
надо запускать непосредственно перед прогоном, не заранее — README и
делает это явно двумя соседними шагами.

## Реплики
